# РАР-6.2. Следующая версия схемы базы (v5): проект

Черновик от 22.11.2026. Статус: **на обсуждение, не утверждён.** Подготовлен субагентом-проектировщиком;
архитектор прочитал целиком и выборочно сверил с кодом названия таблиц, функций и видов действующего лица. Это проектный документ этапа 6.2
из [rar-roadmap.md](../rar-roadmap.md) (раздел РАР-6) и ответ на исследование И6. Код по нему не
менялся, база не переносилась.

## 1. Зачем и что меняется для человека

Сейчас программа считает, что за компьютером один человек. Ответ на карточку хранится как одно
значение на место: новый ответ затирает прежний, автора отдельного ответа часто нет, а момент
«решение принято» не отделён от момента «человек что-то ответил». Для экрана на телефоне,
для нескольких участников и для поручения ИИ этого мало.

Что изменится для человека после схемы v5 и следующих за ней этапов:

- каждый ответ на карточку сохраняется отдельно: кто ответил, с какого устройства, когда, что
  написал. Прежние ответы не пропадают, их видно в истории места;
- отдельно видно, **кто и когда принял решение** по месту: Анна ответила, Борис принял;
- в каждом действии видно, кто его сделал: человек, ИИ по поручению (и по чьему), модель или
  сама программа;
- поручение ИИ хранится в базе вместе с тем, кто его дал и когда сузил или расширил;
- телефон подключается сопряжением с подтверждением на компьютере и может быть отозван;
- у голосового профиля появляется «человек, чей это голос», и запись о его согласии.

**Чего документ не делает.** Не меняет код, базу и установленную программу. Не переносит данные:
перенос на каждой установке согласуется отдельно (раздел 9 — только путь и проверки). Не выбирает
экраны (это этапы 6.3–6.6) и не решает вопросы шифрования (6.7) и сервиса для посторонних (6.9).

## 2. Что есть в схеме v4 сейчас

Проверено по `storage.py` (`SCHEMA_VERSION = 4`), `recordings.py`, `review_pack.py`,
`workflow.py` на ветке `main` от 22.11.2026.

### 2.1. Люди, установки, действия

| Таблица | Поля | Что значит |
|---|---|---|
| `local_users` | `user_id` (UUID), `display_name`, `created_at`, `updated_at` | участник; имя свободное, тёзки не сливаются |
| `installations` | `installation_id`, `current_user_id` → `local_users`, `active` | копия программы и чей она; активна ровно одна (`current_identity`) |
| `operations` | `operation_id`, `kind`, `parameters_hash`, `context_json`, `result_json`, `author_user_id`, `initiator_user_id`, `installation_id`, `created_at` | журнал действий и защита от повтора (тот же `operation_id` с теми же параметрами возвращает прежний результат) |

Контекст действия (`storage._context`) — четыре поля: `actor_kind` (`human`, `model`, `system`,
`unknown`), `author_ref`, `initiated_by`, `origin_installation_id`. У действия модели или системы
автора-человека нет, человек указывается как инициатор. Вида «ИИ по поручению» нет.
Устройства, сеанса и канала (страница, терминал, MCP) в контексте нет.

### 2.2. Записи и их ревизии

- `recordings` — запись и указатели на текущие ревизии (`source_revision`, `review_revision`).
  **Владельца, пространства и группы у записи нет.** Группа записи лежит только внутри снимка
  стенограммы, в поле `quality.runtime.group` (JSON).
- `transcript_revisions` и `review_revisions` — неизменяемые снимки (JSON целиком, `payload_hash`),
  номер ревизии — целое число внутри записи, у каждой ревизии `operation_id`. Возврат версии
  (`restore_as_new_revision`) создаёт новую ревизию со ссылкой `restored_from`.
- Документы: `document_versions`, `document_outbox`, `file_locations`, `document_conflicts`,
  `materialization_events`; конспекты: `conspects`, `conspect_revisions`, `conspect_outbox`,
  `conspect_file_locations`, `conspect_conflicts`. Процесс П3: таблицы `workflow_*`.

### 2.3. Карточки, ответы и события — внутри снимка разбора

Всё, что относится к разбору, хранится JSON-полями снимка `review_revisions.payload`
(`storage.REVIEW_FIELDS`):

| Поле снимка | Что в нём | Ограничение |
|---|---|---|
| `review` | места разбора (`id` вида `r5`, причины, `status`: `open` / `human` / `resolved`, отметка прослушивания) | `id` уникален только внутри записи |
| `questions`, `question_version` | вопросы текущего пакета карточек | версия пакета одна на запись |
| `answers` | **словарь «номер места → один ответ»** | второй ответ на то же место заменяет первый; в силе «более поздний по `ts`» (`review_pack._add_answers`) |
| `conflicts`, `rejected` | расхождения ответов из разных режимов, отклонённые ответы | |
| `applications`, `undo.review_pack` | применение ответов, снимки отмены, `applied_answers` | |
| `interaction_events` | события показа карточки и плеера | не больше 2000, старые вытесняются со счётчиком |

Следствия, важные для проекта:

1. **Каждый сохранённый ответ и каждое событие показа создают новую полную ревизию разбора**
   (`recordings.write_review_pack_state`, `storage.commit_player_event`). История ответов
   сохраняется только неявно — в прежних ревизиях.
2. Автор ответа есть, только если ответ пришёл в режиме `sqlite`: к ответу дописываются
   `actor_kind`, `author_ref`, `initiated_by` из текущей установки. В режиме `legacy_files`
   (`answers.json` в папке `<запись>.review`) и в перенесённых старых ответах автора нет
   (и по правилу `legacy-migration.md` он не придумывается).
3. Событий показа два вида с разной формой: в `review_pack.add_interaction_event` есть номер
   места, версия пакета, сеанс страницы и время, но нет автора; в `storage.commit_player_event`
   есть контекст автора, но нет номера места. Время в `review_pack._now` пишется без пояса
   (`ГГГГ-ММ-ДДTЧЧ:ММ:СС`), в `storage._now` — ISO с `+00:00`.
4. «Решение» как отдельной сущности нет: его роль играют `status` места, `applied_answers`
   и запись в `applications`.

### 2.4. Голоса и поручение

- Голосовые профили — файлы `groups/<группа>/voices.json` и `voice-backups/` в папке данных,
  в базе их нет. Человека-носителя голоса и согласия нет нигде; профиль знает только имя.
- Поручение ИИ по плану этапа 6.1 до схемы v5 хранится в отдельном файле
  `<папка данных>/ai-delegation.json` с журналом изменений; решение по месту и отметка
  «решено по поручению» — в самом месте разбора.

### 2.5. Чего не хватает

| Нужно по решениям владельца | В v4 |
|---|---|
| пространство и участники с ролью | нет; есть только `local_users` |
| устройства, сопряжение, отзыв, сеансы | нет |
| ответ строкой с автором и временем | нет: один ответ на место внутри JSON |
| принятое решение: кто и когда | нет: только статус места |
| вид действующего лица «ИИ по поручению» | нет: `human` / `model` / `system` / `unknown` |
| поручение ИИ с уровнями | только в файле (план 6.1) |
| показ карточки, переслушивания, время до ответа | частично, в JSON, до 2000 событий |
| примечание человека отдельно от ответа | нет |
| человек-носитель голоса, согласие | нет |
| связь пространства с группой голосов | нет: группа — папка и поле JSON |

## 3. Общие правила новой схемы

- **Строки только добавляются.** Ответы, показы, решения, поручения, согласия не исправляются
  на месте: изменение — новая строка со ссылкой на прежнюю. Так история не теряется, а синхронизация
  с телефоном и будущим сервером сводится к «передать новые строки».
- **Снимки ревизий остаются как есть.** Существующие `payload` и их хэши не переписываются.
  Новые таблицы ссылаются на ревизии и действия (`operations`), а не заменяют их.
- **Время** — UTC, ISO 8601 с миллисекундами и `Z`, одной функцией. Время с устройства хранится
  отдельно (`client_at`) и для порядка не используется: часы телефона могут врать.
- **Пространство** (`workspace_id`) — во всех корневых и самостоятельно читаемых таблицах
  (записи, группы, ответы, показы, решения, поручения, носители голоса). У ревизий оно выводится
  через запись. Это готовит разделение данных для сервиса, но не требует его сейчас.
- Новые таблицы объявляются `STRICT` (строгие типы), булевы — 0/1 с `CHECK`, `foreign_keys=ON`
  уже включён в `storage._connect`. Номер схемы — по-прежнему `store_meta.schema_version`.

## 4. Предлагаемые сущности и таблицы

Типы: `TEXT` UUID — строка UUID в каноническом виде (как сейчас проверяет `storage._uuid`);
«действие» — ссылка на `operations.operation_id`. Поля «кто» везде — `user_id` из `local_users`.

### 4.1. Пространство, участник, членство

| Таблица | Поля | Ключи и ссылки |
|---|---|---|
| `workspaces` | `workspace_id` TEXT, `name` TEXT, `created_at`, `created_by` | PK `workspace_id` |
| `local_users` (есть) | + `status` TEXT (`active` / `disabled`), + `disabled_at` | имя остаётся в этой таблице |
| `workspace_members` | `workspace_id`, `user_id`, `role` TEXT (`owner` / `member`), `added_at`, `added_by`, `removed_at`, `removed_by` | PK (`workspace_id`, `user_id`, `added_at`); → `workspaces`, `local_users` |
| `voice_groups` | `group_id` TEXT, `workspace_id`, `folder_name` TEXT, `created_at` | PK `group_id`; UNIQUE (`workspace_id`, `folder_name`); `folder_name` — нынешнее имя папки `groups/<группа>` |
| `recordings` (есть) | + `workspace_id` NOT NULL, + `group_id` NULL | → `workspaces`, `voice_groups` |

Пространство — круг людей, которые видят одни и те же записи. Группа голосов — круг говорящих
и словарь. Одно пространство содержит несколько групп; группа принадлежит ровно одному
пространству; голоса не переходят между пространствами (варианты — раздел 5.1).

### 4.2. Устройство, сопряжение, сеанс

| Таблица | Поля | Ключи и ссылки |
|---|---|---|
| `installations` (есть) | без изменений | сервер: «этот компьютер» |
| `devices` | `device_id`, `user_id`, `installation_id`, `name` TEXT, `kind` TEXT (`local_browser` / `phone` / `computer`), `paired_at`, `approved_by`, `last_seen_at`, `revoked_at`, `revoked_by` | → `local_users`, `installations` |
| `device_pairings` | `pairing_id`, `code_hash` TEXT, `requested_name`, `created_at`, `expires_at`, `approved_at`, `approved_by`, `device_id` NULL | короткоживущая заявка; код хранится только хэшем |
| `device_sessions` | `session_id`, `device_id`, `token_hash` TEXT UNIQUE, `created_at`, `expires_at`, `last_seen_at`, `revoked_at` | → `devices`; сам токен в базе не хранится |

Сопряжение: телефон показывает или вводит короткий код, человек подтверждает его на компьютере
окном программы, устройству выдаётся случайный токен, в базу пишется только его хэш. Отзыв
устройства гасит все его сеансы. Браузер на самом компьютере (`127.0.0.1`) — тоже устройство
вида `local_browser`, сопрягается один раз автоматически при первом входе владельца. Агент через
MCP устройством не является: его канал записывается в действии (4.4).

При резервной копии (`Store.backup`) вместе с `installations.active=0` все сеансы копии
гасятся (`device_sessions.revoked_at`): восстановленная копия не должна пускать старые телефоны.

### 4.3. Место, вопрос, показ, ответ, решение, примечание

| Таблица | Поля | Ключи и ссылки |
|---|---|---|
| `review_places` | `place_id`, `recording_id`, `workspace_id`, `item_key` TEXT (нынешний `r5`), `created_at`, `created_by_operation` | UNIQUE (`recording_id`, `item_key`); устойчивое имя места на все ревизии |
| `review_questions` | `question_id`, `place_id`, `pack_version` TEXT, `card_revision` INTEGER, `kind` TEXT (`normal` / `contradiction`), `base_source_revision`, `payload` TEXT (JSON: вопрос, варианты, слова, которые видел человек), `created_at`, `supersedes_question_id` | → `review_places`; ответ всегда относится к конкретной редакции карточки |
| `review_shows` | `show_id`, `question_id`, `workspace_id`, `user_id`, `device_id` NULL, `session_id` NULL, `shown_at`, `client_at` | одна строка — один показ карточки на одном устройстве |
| `review_show_events` | `event_id`, `show_id`, `type` TEXT (`play`, `ended`, `widen_before`, `widen_after`, `hidden`), `at`, `client_at` | → `review_shows`; только добавление |
| `review_answers` | `answer_id`, `question_id`, `place_id`, `workspace_id`, `show_id` NULL, `text` TEXT NOT NULL, `parsed` TEXT (JSON: вид, номер варианта, версия разборщика), `source` TEXT (`page`, `phone`, `cloud`, `import`, `migrated`), `operation_id`, `created_at`, `client_at`, `state` TEXT (`submitted` / `withdrawn` / `rejected`), `reject_reason`, `supersedes_answer_id` | → `review_questions`, `review_shows`, `operations` |
| `review_decisions` | `decision_id`, `place_id`, `workspace_id`, `kind` TEXT (см. 6.1), `answer_id` NULL, `question_id` NULL, `outcome` TEXT (JSON: что стало со словами и говорящим), `listened` TEXT (`yes` / `no` / `unknown`), `operation_id` NOT NULL, `result_source_revision`, `result_review_revision`, `supersedes_decision_id`, `decided_at` | → `review_places`, `review_answers`, `operations`; кто принял — через действие |
| `review_notes` | `note_id`, `place_id`, `question_id` NULL, `decision_id` NULL, `text`, `operation_id`, `created_at`, `supersedes_note_id` | примечание человека; в `.md`, конспект и модельное задание не выводится |

Как это читается простыми словами:

- **место** — одно сомнительное место записи, переживает пересборку карточек;
- **вопрос** — конкретная редакция карточки об этом месте; пересборка одной карточки (например,
  карточка противоречия) даёт новую редакцию только ей, остальные ответы не сбрасываются;
- **показ** — человек открыл карточку на устройстве; события показа считают переслушивания
  и сдвиги границ; время до ответа = `review_answers.created_at − review_shows.shown_at`;
- **ответ** — всегда текст, как его увидел и отправил человек; разбор текста («это вариант 2»)
  хранится рядом и может быть пересчитан, исходный текст не меняется;
- **решение** — то, что реально применено к стенограмме, со ссылкой на ответ и на действие,
  в котором видно, кто и когда его принял.

Решение владельца 6 («показ и ответ — одна запись») выполняется так: показ и ответ — разные
строки одного журнала, ответ ссылается на показ. Отдельной таблицы «статистики показа» нет:
всё для этапа 5.1 считается запросом по этим двум таблицам.

Голосовой ответ: звук отправляется на компьютер, текст возвращается в поле, в базу попадает
только текст. Хранить ли звук ответа — вопрос владельцу (раздел 12, вопрос 6).

### 4.4. Действие и вид действующего лица

Отдельной таблицы «действий» не вводится: журналом остаётся `operations`. В неё добавляются:

| Новое поле `operations` | Значение |
|---|---|
| `actor_kind` TEXT | `human`, `ai_delegated`, `ai`, `model`, `system`, `unknown` |
| `workspace_id` NULL | в каком пространстве |
| `device_id` NULL, `session_id` NULL | с какого устройства и сеанса |
| `channel` TEXT NULL | `page`, `phone`, `terminal`, `mcp`, `worker`, `migration` |
| `delegation_id` NULL | по какому поручению действовал ИИ |

Виды действующего лица:

| Вид | Кто | Автор-человек | Что может |
|---|---|---|---|
| `human` | участник сам, со страницы, телефона или терминала | да | всё, что разрешает роль |
| `ai_delegated` | агент ИИ по поручению | нет; `initiated_by` — давший поручение | только то, что поручено; `delegation_id` обязателен |
| `ai` | агент ИИ без поручения | нет | только предложения (ответ-предложение на карточке) |
| `model` | модели распознавания и конспекта | нет | создавать содержимое в процессе обработки |
| `system` | программа: перенос, пересборка, обслуживание | нет | служебные действия |
| `unknown` | только старые записи | нет | ничего нового не пишется с этим видом |

Правило проверки — в одном месте (`storage._context`): `ai_delegated` без `delegation_id`
отклоняется; у видов, кроме `human`, автор-человек пустой, как сейчас.

### 4.5. Поручение ИИ

| Таблица | Поля |
|---|---|
| `ai_delegations` | `delegation_id`, `user_id` (за кого работает ИИ), `scope_kind` TEXT (`program`, `workspace`, `group`, `recording`, `place`), `scope_id` NULL, `part` TEXT (`words`, `pauses`, `speaker`, `overlap`, `left_to_me`), `mode` TEXT (`self`, `suggest`, `do`), `operation_id`, `created_at`, `supersedes_delegation_id` |

Части и положения — как в плане 6.1 (слова, паузы, кто говорит, одновременная речь, оставленные
мне; «сам», «ИИ предлагает», «ИИ делает за меня»). Готовые наборы — это несколько строк одним
действием. Строка не меняется: новое положение — новая строка; действует последняя по
(`user_id`, `scope_kind`, `scope_id`, `part`).

**Порядок разрешения** для каждого действия агента (одна функция, без вариантов по кнопкам):

1. Действие задевает слово или решение человека → карточка противоречия при любой настройке.
2. У места есть индивидуальное решение («Решу сам» / «Поручить ИИ») — строка уровня `place`.
3. Место оставлено человеком → часть `left_to_me`.
4. Иначе — части по причинам места и по виду действия.

В пунктах 3–4 каждая часть берётся с ближайшего уровня, где задана:
**место → запись → группа → пространство → программа → умолчание `suggest`**. При нескольких
частях действует самое строгое положение. Неизвестная или противоречивая группа — групповой
уровень пропускается, и положение не сильнее `suggest`.

Расширять поручение может только человек через окно программы или терминал (`confirm.py`),
сужать — одной кнопкой. Действие ИИ по поручению: закрывает место с `listened = no`; такое место
не держит цитату; смена говорящего — только при явной части `speaker` и не идёт в голосовые
профили (в `outcome` решения ставится признак `not_for_voice_training`).

### 4.6. Человек-носитель голоса и согласие

| Таблица | Поля |
|---|---|
| `voice_subjects` | `subject_id`, `workspace_id`, `display_name`, `user_id` NULL (если это сам участник программы), `created_at`, `created_by` |
| `voice_profile_links` | `group_id`, `profile_name` TEXT (имя в `voices.json`), `subject_id`, `linked_at`, `linked_by`, `unlinked_at` |
| `voice_consents` | `consent_id`, `subject_id`, `scope` TEXT (`store_profile`, `learn_from_recordings`), `basis` TEXT (`self`, `oral`, `written`, `not_recorded`), `given_at`, `recorded_by`, `withdrawn_at`, `withdrawn_by`, `note` |

Отпечатки голоса остаются в файлах `voices.json`: в базу они не переносятся (раздел 7). База
знает, чей это голос и есть ли согласие. На обкатке отсутствие согласия только показывается;
блокировать обучение без согласия — решение владельца (вопрос 8). Отзыв согласия по действующей
[политике биометрии](../voice-biometrics-policy.md) не удаляет профиль сам: удаление — отдельное
подтверждённое действие с резервной копией.

### 4.7. Схема связей

```text
workspaces ─┬─ workspace_members ── local_users ── devices ── device_sessions
            │                            │             └── device_pairings
            ├─ voice_groups ── voice_profile_links ── voice_subjects ── voice_consents
            ├─ recordings ─┬─ transcript_revisions / review_revisions (как в v4)
            │              └─ review_places ── review_questions ─┬─ review_shows ── review_show_events
            │                        │                           └─ review_answers
            │                        ├─ review_decisions ──→ operations (кто, вид лица, устройство,
            │                        └─ review_notes              поручение) ──→ ai_delegations
            └─ ai_delegations (уровни: программа, пространство, группа, запись, место)
```

## 6. Одна точка записи решения

### 6.1. Правило

Все пути, которые меняют судьбу места, идут через одну функцию — условно
`review_decisions.decide(store, place_id, kind, *, answer_id=None, outcome, context,
expected_versions)` в новом модуле. Её вызывают: применение ответов (страница, `rt.py`, MCP
`apply_answers`), прямые решения `apply_review`, `edit_span` (через проверку противоречия),
`reopen_review`, действия ИИ по поручению, возврат версии, подтверждение импортированного ответа
(`request_review_answer_verification`). Другого кода, пишущего `review_decisions` или `status`
места, нет.

Виды решения (`kind`): `accept_answer` (принят ответ человека), `ai_delegated` (решено ИИ
по поручению), `direct` (прямое решение человека без карточки), `left_to_human` («Оставить
человеку»), `reopen` (место снова открыто), `revert` (отмена прежнего решения), `restored`
(состояние места после возврата версии), `migrated` (перенесено из v4).

В одной транзакции функция:

1. проверяет роль (5.3) и поручение (4.5) — для `ai_delegated`;
2. проверяет противоречие: правка задевает слово под действующим решением человека → решение не
   пишется, создаётся вопрос `kind = contradiction` с вариантами (каждый с автором, временем
   и путём) и местом для примечания; текст стенограммы не меняется;
3. сверяет `expected_versions` (как сейчас `commit_change`);
4. пишет новую ревизию стенограммы и разбора тем же `commit_change_with_document`;
5. пишет строку `review_decisions` со ссылкой на действие и на получившиеся ревизии.

### 6.2. Как из ответов получается решение

- **Ответ — не решение.** Ответ записывается сразу, ничего не меняя в тексте. Решение возникает,
  когда участник нажимает «Применить» (как сейчас `apply_answers`): одно действие создаёт
  решения по всем выбранным ответам, автором решения записывается применивший.
- Если на один вопрос есть ответы нескольких людей и они **совпадают** по разобранному смыслу —
  применяется один, в решении перечислены все совпавшие ответы (поле `outcome`).
- Если ответы **расходятся** — пакетное «Применить» место пропускает и показывает оба ответа;
  решение принимает любой участник явным выбором одного из них или своим текстом.
- Свой ответ после своего же прежнего — «Изменить ответ»: новая строка ответа
  с `supersedes_answer_id`; если прежний уже применён — решение `revert` и новое решение
  одной операцией или никак (как в плане этапа 6.1).
- Действующее решение места — последнее по времени, не заменённое другим
  (`supersedes_decision_id`). Пересмотр — новое решение; отмена — решение `revert`, после которого
  место открыто.

### 6.3. Как это ложится на ревизии записи

- Каждое решение, менявшее текст, указывает на ревизии, которые оно создало. Отмена использует
  существующий снимок отмены (`undo`) и тоже создаёт новые ревизии — ничего не стирается.
- **Возврат версии** (`restore_recording_revision`) проходит через ту же функцию: для каждого
  места, у которого действующее решение отличается от состояния в возвращённой ревизии, пишется
  решение `restored` с автором возврата. Ответы при этом не трогаются: они остаются и могут быть
  применены снова.
- Снимок разбора продолжает хранить `status` и отметку прослушивания места: по нему строятся
  документы и проверяется запрет цитат. Таблица решений — журнал «кто, когда, почему», снимок —
  итог. Расхождение итога и журнала — ошибка, которую ловит `validate_copy`.

### 6.4. Ручная правка слабее ответа

`edit_span` от человека, задевающий слово, подтверждённое карточкой, не меняет текст, а создаёт
карточку противоречия (решение владельца 5). Ответ на неё — обычный ответ; примечание —
отдельной строкой `review_notes`, в текст не попадает. Человек карточкой может перекрыть правку
ИИ сразу: «человек главнее» (порядок приоритетов из `AGENTS.md`).

## 8. Права: сейчас и для посторонних

**Сейчас (обкатка, все доверенные).** Каждый участник пространства видит все его записи
и может всё: отвечать, принимать решения, давать поручение ИИ за себя, подключать устройства
к своей учётной записи. Ограничения, которые действуют и на обкатке:

- поручение ИИ даёт каждый **за себя**; расширение — только окном программы или терминалом;
- сопряжение нового устройства подтверждается на компьютере; отзыв — сразу;
- сервер по умолчанию слушает только `127.0.0.1`; домашняя сеть включается человеком;
- агент не может назвать себя человеком (`--by human` под проверкой, план 6.1).

**Что добавить для посторонних (этап 6.9), не строя сейчас:** роли сверх `owner` / `member`
(например «только чтение»), права на отдельную запись, приглашения, вход по паролю или ключу
доступа (нужны доменное имя и шифрование), раздельные папки данных по пространствам, обязательное
согласие носителя голоса до обучения, журнал доступа к профилям, сроки хранения и настоящее
удаление при отзыве, возможно переход на PostgreSQL. Путь открыт тем, что уже есть: пространство
в корневых строках, роль, одна функция проверки, автор и устройство в каждом действии.

## 9. Идентификаторы

| Вариант | Плюсы | Минусы |
|---|---|---|
| Целые числа по порядку | короткие | сталкиваются при слиянии баз, при `export_group` / `import_group` между установками и при синхронизации |
| UUID v4 (как сейчас) | не сталкиваются; уже везде; проверка `storage._uuid` | случайный порядок — индексы по времени хуже; время создания не видно |
| **UUID v7 для новых строк журнала** | не сталкиваются; упорядочены по времени; тот же текстовый вид — проходит ту же проверку | в Python 3.11–3.13 (их ставит `install.ps1`) готовой функции нет, нужна своя на несколько строк; раскрывает время создания — не годится как секрет |
| ULID | упорядочен | другой текстовый вид: не проходит `storage._uuid`, две формы ID в базе |

**Рекомендация.** Новые строки журналов (`review_answers`, `review_shows`, `review_show_events`,
`review_decisions`, `ai_delegations`, `voice_consents`) — UUID v7; остальные новые сущности
и все существующие ID — как есть (v4). Существующие ID не перевыпускаются. Номера ревизий
остаются целыми внутри записи: их выдаёт сервер, и столкновений нет, пока пишет один сервер.
Токены устройств — 32 случайных байта, в базе только хэш.

**Связь с синхронизацией.** Телефон на обкатке — тонкий клиент: все записи идут через сервер.
Клиент сам создаёт `answer_id` до отправки, поэтому повтор отправки после обрыва связи не создаёт
второй ответ (как сейчас `operation_id`). Работа телефона без связи и слияние двух серверов
не планируются; при сервисе строки «только добавление» с UUID v7 переносятся без перенумерации.

## 10. Путь переноса с v4

Перенос на установке владельца — отдельное согласование; ниже — как он должен выглядеть.

### 10.1. Что может задеть в настоящей установке

| Что | Как задевается | Обратимо |
|---|---|---|
| `state.sqlite3` в папке данных (+ `-wal`, `-shm`) | **не меняется**: новая база строится рядом во временном файле и подставляется только после проверки | да, пока не начали работать в v5 |
| резервные копии базы (`db-backup`) | перед переносом делается новая; старые не трогаются и не удаляются | — |
| `ai-delegation.json` | читается, переносится в `ai_delegations`; файл остаётся как архив | да |
| `groups/*/voices.json`, `voice-backups/` | только чтение имён профилей; не пишутся | — |
| документы рядом с аудио (`.md`, `.json`, `history/`) | при неизменном формате документов не перезаписываются; если формат меняется — пересборка отдельным шагом по согласию | нет после пересборки (старое — в `history/` и в резерве) |
| папки `<запись>.review` (клипы, `answers.json`, `voice/`) | только чтение | — |
| `jobs/`, аудиофайлы | не затрагиваются | — |
| ссылки (junction, symlink) в папке данных | новая база публикуется жёсткой ссылкой (`os.link`), как `storage.initialize` — нужен тот же диск; сетевые диски отклоняет `check_local_path` | — |

**Точка необратимости:** после переключения программа v5 не откроет базу v4, а прежняя версия
программы не откроет v5 (`_check_schema` требует точный номер). Ответы, данные в v5, в базу v4
не вернутся. Откат — вернуть резервную копию и прежнюю версию программы, потеряв сделанное после.

### 10.2. Шаги

1. Обновление программы до версии, умеющей v5; перенос не запускается сам (как правило
   `tests/test_no_auto_migrate.py`).
2. Резервная копия: `db-backup`, копия `ai-delegation.json`, контрольные суммы.
3. Проверка без записи: отчёт «сколько мест, ответов, событий, групп; что неоднозначно».
4. Построение новой базы во временном файле: схема v5, перенос строк из v4 (ниже).
5. Проверка временной базы (`validate_copy` в версии v5 и сверка с v4).
6. Подстановка новой базы, перезапуск программы; старый файл остаётся рядом под другим именем.

### 10.3. Что и как переносится

- Одно пространство «Основное»; все `local_users` — его участники; пользователь активной
  установки — `owner`, остальные — `member`.
- Группы — по папкам `groups/`; `recordings.group_id` — по `quality.runtime.group` текущей
  ревизии, если группа есть среди папок; иначе пусто и строка в отчёте.
- Места — по `review` текущей ревизии разбора, `item_key` = прежний `id`.
- Вопросы — по `questions` и `undo.review_pack.manifest` текущей ревизии.
- Ответы: из `answers` всех ревизий разбора (так восстанавливается история «один затёр другой»)
  с их `ts` и автором, **если он записан**; иначе `actor_kind = unknown`. Автор не придумывается
  и «владельцем» не заполняется.
- Решения: по `status` мест и `applications` — решение `migrated` с автором из контекста
  применения, если он есть.
- События: `interaction_events` → показы и события, сгруппированные по сеансу и месту, с пометкой
  «перенесено»; число вытесненных событий — в отчёт.
- Поручение — из `ai-delegation.json` с его журналом.
- Носители голоса: по одному на имя профиля **только по решению владельца** (вопрос 8); иначе
  таблица пустая, а программа показывает «носитель не указан».
- `operations`: новые поля у старых строк пустые.
- Существующие снимки ревизий, их хэши и документы не переписываются.

## 11. Что не проверено и что проверить пробой на копии (И6)

Не проверено по коду или вообще:

- что построитель документов (`documents.py`) выдаёт **те же байты**, читая ответы из таблицы, —
  от этого зависит, будут ли перезаписаны файлы рядом с аудио;
- сколько ответов реально «затёрто» в истории ревизий на установке владельца и восстанавливается
  ли их порядок по `ts` (разные форматы времени, см. 2.3);
- поддержка `STRICT` на других установках (нужна SQLite 3.37 или новее; на компьютере владельца
  проверено 22.11.2026: SQLite 3.49.1, Python 3.12.10);
- как группа записи хранится в старых и перенесённых записях (только ли `quality.runtime.group`);
- сколько места и времени займёт перенос; рост базы при показах без полных ревизий;
- поведение при одновременных ответах двух устройств на одну карточку (`BEGIN IMMEDIATE`,
  `busy_timeout` уже есть, но под нагрузкой не проверялись);
- согласованность снимка разбора и журнала решений после отмены и возврата версии.

Проба на копии базы (в песочнице с отдельными `RUS_TRANSCRIBER_DATA`, `TEMP`, `TMP`):

1. перенос копии v4 → v5; сверка числа мест, вопросов, ответов, решений и событий с источником;
2. `integrity_check`, `foreign_key_check`, расширенный `validate_copy`;
3. формирование документов по всем записям и побайтовое сравнение с существующими;
4. сценарий «Анна ответила с телефона, Борис ответил иначе, Анна приняла» на синтетике;
5. сценарий «ИИ по поручению закрыл место — человек вернул» и «возврат версии»;
6. резервная копия v5 гасит сеансы устройств;
7. замер размера базы и времени переноса.

## 13. Где отчёт поиска (источник 11) расходится с кодом

- «Пользователи и устройства — добавить»: `local_users`, `installations` и автор, инициатор
  и установка в `operations` в v4 **уже есть**; не хватает устройств, сеансов и пространства.
- «Для существующих строк автор — владелец, заполнить один раз»: противоречит контракту
  (`storage-contract-v1.md`, `legacy-migration.md`): неизвестный автор остаётся неизвестным.
- «Пространство = ваша группа»: группа в коде — папка `groups/<группа>` с голосами и словарём,
  а в базе только поле JSON `quality.runtime.group`; это не таблица и не круг доступа.
- «`actor_kind`: человек, модель, система»: в коде уже четыре вида (`unknown` для старого)
  и раздельные автор и инициатор; вида «ИИ по поручению» нет ни там, ни там.
- «`workspace_id NOT NULL` во всех таблицах»: для неизменяемых ревизий, привязанных к записи,
  избыточно; группа записи бывает неизвестна — обязательная группа заставила бы угадывать.
- «`PRAGMA user_version`»: в проекте номер схемы — `store_meta.schema_version`, функции обновления
  схемы нет вовсе; её придётся написать впервые.
- «Журнал событий — добавить автора и пространство»: событий как таблицы нет; они лежат в JSON
  снимка разбора с пределом 2000 и в двух разных формах.
- «Отзыв согласия ведёт к физическому удалению»: это ориентир для сервиса; действующая политика
  биометрии запрещает удаление без прямого решения владельца.
- «Время как придётся → UTC»: в коде уже два разных формата UTC (`review_pack._now` без пояса,
  `storage._now` с `+00:00`).
