### Как читать и чему не верить
- Даты, лицензии и звёзды взяты из GitHub API (`api.github.com/repos/...`) через WebFetch. Их пересказывала маленькая модель, поэтому я не перепроверял их вручную.
- `pushed_at` не равен «поддерживается». У репозиториев BBC он ноябрьский, но их README пишет, что BBC не ведёт разработку. У Gecko push датирован 01.12.2025, а README объявляет его deprecated с ноября 2025.
- Страницы не помечал как «только аннотация» там, где читал полный текст. «Только аннотация или часть» отмечено отдельно у каждого пункта.
- Две PDF-статьи (FAST, LREC-2016 Sperber) не читались: WebFetch отдал бинарные потоки. По ним есть только вторичные пересказы из выдачи поиска.
- Названия проекта в запросы не подставлял.

#### Связь слова и звука, говорящие, навигация по сомнительным, клавиши, история

Здесь только то, что нашёл. «Нет данных» не значит «функции нет».

- **noScribe Editor.** Ctrl+Space запускает звук с позиции курсора, выделение текста идёт за звуком. Есть выпадающий список скорости, масштаб, поиск и замена: так предлагают менять имена говорящих. В v0.8 добавлена полоса перемотки внизу, синхронная с текстом ([инструкция](https://noscribe.de/en/docs/usage/)). Подсветки сомнительных слов в прочитанном нет. «Текстовые якоря-метки времени в HTML» — это из стороннего пересказа поиска, не из первоисточника.
- **Scriberr.** Звук идёт за текстом, переход по клику на текст, пословные тайминги, диаризация. Правку текста README прямо не называет.
- **BBC react-transcript-editor.** Двойной клик по слову ставит время. Слово подсвечивается по ходу воспроизведения, прокрутка за ним по умолчанию выключена. Имена говорящих на уровне абзаца, редактируются. Есть переход по таймкоду и настраиваемая кнопка отката (по умолчанию 15 с). Сохранение таймкодов при правке на момент документа «not yet done», кастомные горячие клавиши тоже ([features-list](https://raw.githubusercontent.com/bbc/react-transcript-editor/master/docs/features-list.md)).
- **Hyperaudio Lite.** Каждое слово в HTML несёт `data-m` (начало, мс) и `data-d` (длительность), клик ведёт к звуку; поиск, скорость ([README](https://raw.githubusercontent.com/hyperaudio/hyperaudio-lite/master/README.md)). Редактор: имена говорящих как `[Мария]`, разбиение и слияние абзацев, найти-заменить, автосохранение проектов в браузере, ⌘S ([README](https://raw.githubusercontent.com/hyperaudio/hyperaudio-lite-editor/master/README.md)). Вставка больших блоков текста ломает пословные тайминги, поэтому её не рекомендуют.
- **Label Studio.** В Community: шаблон «аудио + TextArea» и вариант с TextArea на каждый сегмент. Платная «продвинутая» транскрипция только в Enterprise: аудио слева, текст справа, клик по волне ведёт к тексту и наоборот. Сегменты двигают, делят и сливают на таймлайне «без режимов и модальных окон»; почти всё доступно с клавиатуры; у каждого аннотатора свои настройки, например отключение подтверждений ([блог HumanSignal](https://humansignal.com/blog/building-a-better-ui-for-audio-transcription-at-scale/)). Цифр прироста там нет.
- **Subtitle Edit.** Горячие клавиши по группам (общие, таблица, текст, волна) настраиваются, экспорт в JSON. Умолчания в прочитанной странице не перечислены ([страница](https://niksedk.github.io/subtitleedit-avalonia/features/shortcuts.html)). В 5.1.0 есть «AI review» через локальную модель (по вторичному источнику).
- **Gecko.** Сравнение разметок разных систем и аннотаторов, правка диаризации, показ нескольких источников. Клавиши есть, но не перечислены.
- **ELAN.** Режим Transcription и таблица клавиш есть в [руководстве](https://www.mpi.nl/tools/elan/docs/manual); содержимое не читал.
- **Descript.** Отдельный режим «Correct»: правка меняет только текст, звук не трогает, потом тайминг пересчитывается. Клавиша `C` правит слово, `Alt/Opt+C` включает режим массовой правки, Z и X плюс клик меняют регистр и пунктуацию ([справка](https://help.descript.com/script-editing/correct-your-transcript)). Замена говорящего «во всём проекте» ([справка](https://help.descript.com/script-editing/speaker-labels)). Мобильное приложение и подсветку неуверенности не нашёл.
- **Trint.** Мобильная правка: режим Edit по значку карандаша, подсветка и зачёркивание, undo/redo. Воспроизведения в режиме правки нет. Добавленные или удалённые слова **не сдвигают таймкод** и при воспроизведении могут пропускаться. Правки говорящих в мобильной справке нет ([справка](https://info.trint.com/knowledge/mobile-editing)).
- **Rev, Auphonic, Sonix, Limecraft.** Подсветка слов с низкой уверенностью есть (Rev: меню «Show Low Confidence Words»; Auphonic: Highlight Low Confidence с показом числа при наведении). Sonix предупреждает, что светлое слово не обязательно ошибка ([Sonix](https://help.sonix.ai/en/articles/1756215-how-do-i-use-sonix-s-heatmap-to-identify-potential-errors-in-my-transcript), [Rev](https://www.rev.com/blog/transcript-editor-overview)). Rev: переименование говорящего меняет все вхождения.
- **Happy Scribe.** Список горячих клавиш в меню редактора, свои клавиши настраиваются; слово, звучащее сейчас, синее ([справка](https://help.happyscribe.com/en/articles/6365473-how-to-use-the-shortcuts-in-the-transcript-editor), поиск показал её без чтения: сама страница вернула 403).
- **Transkribus.** Построчная оценка уверенности указана только на маркетинговой странице; как строки с низкой оценкой подсвечиваются и как по ним ходят — не нашёл. Есть режим «рядом»: строка на изображении подсвечивается вместе со строкой текста ([блог Lite 2.1](https://www.transkribus.org/blog/lite2_1)).
- **История правок.** Явной истории ревизий не нашёл ни в одном открытом редакторе. Есть undo: у Audapolis `redux-undo`, у transcribee `slate-history`. Автосохранение: Hyperaudio Lite Editor, Anysub (undo и автосохранение в README), Subtitle Edit.

### Пять–семь проектов, у которых стоит заимствовать

1. **Prodigy + SWAN + FAST (карточки с жестами).** Идея: каждое решение — бинарное «принять / отклонить / пропустить», клавиши `a`, `x`, `space`, `backspace` (отмена), на сенсоре свайпы. Принцип «спрашивай пользователя как можно меньше, остальное угадай» ([блог Explosion](https://explosion.ai/blog/prodigy-annotation-tool-active-learning), [документация](https://prodi.gy/docs/text-classification)). SWAN (MIT, [препринт](https://arxiv.org/html/2511.08271)): четыре направления свайпа, свайп вверх откладывает карточку в конец, возврат назад, продолжение с места остановки, веб на телефоне и ПК. Prodigy закрытый, берутся только идеи.
2. **Scriberr (PWA как путь «со смартфона»).** React + Vite + Tailwind + Radix + wavesurfer, TanStack Virtual для длинных списков, vite-plugin-pwa. Это ближайшая по стеку живая база для адаптивного локального интерфейса. Минус: лицензия есть только в метаданных GitHub, в README не заявлена.
3. **noScribe Editor (минимальная модель прослушивания).** Курсор в тексте = точка звука, выделение идёт за звуком, скорость и поиск-замена под рукой, звуковая полоса внизу. GPL-3 заставляет брать только идеи, если проект не GPL.
4. **Descript Correct mode + замена говорящего «во всём проекте».** Принцип: исправление слова не должно ломать привязку к звуку, сначала правится текст, потом пересчитывается выравнивание. Это решает ровно ту проблему, которую показывает Trint (правки сдвигают таймкод).
5. **BBC react-transcript-editor + Hyperaudio Lite.** Привязка слово → время через `data-m`/`data-d`, подсветка текущего слова, настраиваемый откат на N секунд, прыжок по таймкоду. У RTE ядро на Draft.js, который архивирован, поэтому брать модель данных и идеи, а не код редактора.
6. **Sperber и др., «Transcribing Against Time» (ordering под бюджет усилий).** Выбор и нарезка мест для проверки по оценке выгоды и стоимости, а не по порогу: модель стоимости использует длину в словах, длительность и среднюю уверенность ASR; сегменты в симуляции в среднем около 8 слов (~3 с), максимум 20; стоимость уточняется по ходу работы пользователя; «фиксированный бюджет времени проще, чем порог уверенности» ([ar5iv](https://ar5iv.labs.arxiv.org/html/1709.05227), прочитал полный HTML). Эффект на реальных людях: +15% в среднем, но не значим (p = 0,18; 12 человек, 4 доклада TED).
7. **Label Studio Enterprise (идея макета).** Аудио слева, текст справа, всегда в синхроне; никаких режимов и модальных окон; настройка подтверждений для каждого пользователя. Код этой части недоступен в Community.

### Задача 2. Приёмы со ссылками

#### Что ускоряет проверку и что не доказано

- **Подсветка слов по уверенности сама по себе скорость не дала.** CHI EA 2025 (Kuhn, Kersken, Zimmermann): 36 человек, три условия (без подсветки, порог 0,70–0,88 с ~4% слов, порог 0,99 с 13–21% слов), Whisper, WER ~6%. Снижение WER 0,47 / 0,48 / 0,45, различий нет (p = 0,767); время правки в статье не измерялось. Подсвеченные слова при сбалансированном пороге правили в 2,64 раза чаще. 16 человек предпочли без подсветки, 18 — сбалансированную, 4 — высокую. Из тех 16, кто высказался, 10 назвали подсветку раздражающей, 7 перестали на неё смотреть. Корреляция уверенности с ошибкой r = 0,27–0,54, лучшая точность детектора 0,41–0,55. Авторы советуют подсвечивать редко и объяснять, что подсветка не гарантия ([arXiv HTML](https://arxiv.org/html/2503.15124), прочитал полный текст). Для проекта с 600–700 местами на час это важное предупреждение.
- **QE4PE (перевод, не речь).** 42 профессиональных редактора, четыре способа подсветки: эффект скромный, «разрыв между точностью и удобством» ([arXiv, только аннотация](https://arxiv.org/abs/2503.03044)).
- **Показ вариантов (список альтернатив).** Исследование Microsoft Research: повтор диктовки и выбор из альтернатив самые успешные способы, список нравился больше, хотя точность скромная; если слова в списке нет, пользователи переходят к повтору ([страница, только аннотация](https://www.microsoft.com/en-us/research/publication/speech-error-correction-the-story-of-the-alternates-list/)). Облегчённый, легко открываемый и закрываемый список повысил его использование.
- **Правка черновика ASR против набора с нуля.** По Gaur и др. редактировать быстрее, если WER ниже ~30%; выше этого быстрее печатать самому ([вторичные пересказы в поиске](https://www.cs.cmu.edu/~fmetze/interACT/Publications_files/publications/asr_threshold_w4a.pdf); саму статью не читал). Для плохо распознанных мест полезна кнопка «ввести заново» рядом с вариантами.
- **ASR-помощь ускоряет, но точность не гарантирует.** Simonotti и др., arXiv 17.03.2026, 11 транскрибаторов, итальянский корпус: скорость растёт, точность нестабильна, зависит от конфигурации и опыта ([аннотация](https://arxiv.org/abs/2603.16258)).
- **Короткие сегменты и порядок по пользе.** Sperber: очень короткие сегменты сосредотачивают усилие на ошибочных местах, длинные снижают переключение контекста. Оценка накладных расходов на сегмент сильно улучшала модель: наивные «1 секунда на слово» работали заметно хуже; первичная оценка занижала время на 1–11 с на сегмент ([ar5iv](https://ar5iv.labs.arxiv.org/html/1709.05227)).
- **Модель в цикле ранжирует очередь.** Prodigy: модель обучается по ходу и выбирает следующие примеры, чтобы реже показывать избыточные ([блог](https://explosion.ai/blog/prodigy-annotation-tool-active-learning)). Автор статьи не называет это «uncertainty sampling», это мой вывод.
- **Предзагрузка звука.** Safari давно требует пользовательского жеста; `play()` должен идти из обработчика `touchend`/`click`/`keydown` ([WebKit, 2016](https://webkit.org/blog/6784/new-video-policies-for-ios/)). iOS 10+: `preload="metadata"` соблюдается; `<audio>` без жеста не стартует; скрытые (`display:none`) элементы всё равно требуют жеста. Это данные 2016 года: сторонний текст пишет, что с iOS 17 политика ослабла, и советует проверять на реальном устройстве. [MDN Autoplay](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay): со звуком и без жеста `play()` отклоняется с `NotAllowedError`, нужна видимая кнопка. [MDN Media Session](https://developer.mozilla.org/en-US/docs/Web/API/Media_Session_API): кнопки на экране блокировки и действия вроде `seekto`; поддержка «limited availability».
- **Для длинных записей волну лучше предвычислять.** Peaks.js: расчёт по Web Audio требует скачать весь файл и нагружает процессор; для длинных файлов советуют заранее готовые `.dat`/JSON ([README](https://raw.githubusercontent.com/bbc/peaks.js/master/README.md)).
- **Скорость воспроизведения.** Исследования, где скорость — независимая переменная для правки стенограмм, не нашёл. Есть только патент с автоподбором скорости под пару «говорящий–транскрибатор» (инженерное заявление, не эксперимент).
- **Пакетное подтверждение.** Исследований по «подтвердить всё выше порога» в правке ASR не нашёл. Косвенно: бинарные решения по очереди и «пропустить/отложить» у Prodigy и SWAN.

#### Телефон: карточки, цели нажатия, одна рука

- **Скорость карточек.** FAST (EMNLP 2021 demo): карточки в духе Tinder, свайп или нажатие; на телефоне в среднем 4,7 с на аннотацию против 8,3 с у существующих инструментов, точность ~0,97 (**только вторичный пересказ из выдачи поиска**, PDF не прочитан; [PDF](https://aclanthology.org/2021.emnlp-demo.41.pdf)). SWAN: 1,6–2,8 с на изображение у четырёх патологов, у одного из четырёх быстрее была папочная работа; пилот без статистики, код опубликован анонимно ([arXiv](https://arxiv.org/html/2511.08271)).
- **Размер цели.** [WCAG 2.2 SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html): минимум 24×24 CSS-пикселя (или зазор), для важного рекомендуется 44×44. [NN/g](https://www.nngroup.com/articles/touch-target-size/): минимум 1×1 см, главные кнопки ~2 см; пиксели без плотности экрана ничего не значат; сначала размер, потом отступы.
- **Жесты обязаны иметь альтернативу.** [WCAG 2.5.1](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html) (уровень A): всё, что делается свайпом или многопальцевым жестом, должно выполняться и одним касанием без пути. [NN/g](https://www.nngroup.com/articles/mobile-ux/): жесты — «скрытый альтернативный интерфейс», их трудно открыть и запомнить.
- **Одна рука.** [Hoober, UXmatters 2013](https://www.uxmatters.com/mt/archives/2013/02/how-do-users-really-hold-mobile-devices.php): из 1333 наблюдений 49% — одной рукой, 36% — «в ладони, другой рукой касаются», 15% — двумя руками; 33% одноручных держат левой. Хват меняется «иногда каждые несколько секунд». Сам автор пишет, что позже счёл свои схемы зон досягаемости неточными, их игнорировать. Значит, нужно размещать ключевые кнопки так, чтобы они работали для обоих хватов, а не полагаться на «зону большого пальца».
- **Клавиатура экрана.** [Chrome](https://developer.chrome.com/blog/viewport-resize-behavior): `interactive-widget` (resizes-visual / resizes-content / overlays-content) не действует в iOS и WebView; Safari на iOS изменяет только visual viewport; фиксированные панели ввода могут оказаться под клавиатурой.

#### Адаптивные интерфейсы для данных и редакторов

- **Контейнерные запросы.** [MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_containment/Container_queries): `container-type: inline-size`, `@container`, единицы `cqi`/`cqw`; у контейнера не может быть размера, зависящего от его содержимого. Размерные запросы стабильны в Chrome 105, Edge 105, Firefox 110, Safari 16 ([web.dev](https://web.dev/blog/cq-stable); год на странице не указан).
- **Что отдавать медиа-запросам, что контейнерным.** Практика: макетом страницы (колонки, боковая панель) управляют медиа-запросы, компонентами (карточка, виджет) — контейнерные ([статья-пересказ, вторичный источник](https://dev.to/nickbenksim/container-queries-vs-media-queries-when-and-what-to-use-fij)). Что список-панель с деталями стоит делать собственным контейнером, — моё рассуждение, готового руководства для панелей не нашёл.
- **«Список — подробности».** [Android Developers](https://developer.android.com/develop/ui/compose/layouts/adaptive/list-detail): в большом окне панели рядом, в малом — по одной, деталь занимает весь экран; подсказки по поведению «назад». [Руководство по размерам](https://developer.android.com/develop/ui/compose/layouts/adaptive/support-different-display-sizes): решение о макете принимать по реальной ширине, выделенной компоненту, а не по размеру экрана устройства; компонент всегда получает все данные, даже если на узкой ширине часть не показывает; состояние поднимать выше, чтобы оно не терялось при смене макета. Страница Material 3 для list-detail вернула 404, использовал страницу Android.
- **Что переносится на телефон, а что нет.** Источников, прямо ответивших на этот вопрос, не нашёл. Из прочитанного: у Trint на телефоне правка текста, подсветка, undo есть, но воспроизведения в режиме правки нет, и правки не сдвигают таймкод. Auphonic пишет, что редактор адаптивен для быстрой правки. Моё предположение (не подтверждено ничем): многодорожечный таймлайн, найти-заменить по всему файлу и правка длинного текста на телефон не переносятся; карточка одного места, клип с кнопками и список переносятся.

#### Типичные ошибки (с опорой)

- Подсвечивать слишком много: «раздражает», со временем игнорируют; порог, хороший на одной записи, плох на другой ([Kuhn 2025](https://arxiv.org/html/2503.15124)).
- Принимать «светлое слово = ошибка»: Sonix и Rev прямо пишут, что это не так.
- Жест без кнопки-дубля (нарушение WCAG 2.5.1); мелкие цели; важное в верхнем углу.
- Звук, который стартует не из жеста пользователя (iOS/Safari и MDN).
- Правка текста, ломающая привязку к тайминге (Trint; предупреждение в Hyperaudio про вставку больших блоков).
- Фиксированный порог вместо бюджета усилий; недооценка накладных расходов на сегмент (Sperber).
- Ожидание, что у пользователей один хват и одна рука (Hoober).

### Чего не нашёл
- Открытый редактор с навигацией «следующее сомнительное слово» именно для Whisper: в прочитанных документах noScribe, BBC и Hyperaudio такой функции нет; подсветка уверенности найдена только в закрытых сервисах (Rev, Auphonic, Sonix, Limecraft).
- Отдельные исследования про скорость воспроизведения и про пакетное подтверждение при правке ASR.
- Как именно Transkribus ведёт пользователя по неуверенным строкам (только маркетинг), и подробности Otter/Reduct/Descript на телефоне.
- Руководство по «список — подробности» именно для редакторов в вебе (нашёл Android/Material и общие статьи).
- Версию ELAN 2026 года и лицензию Praat. Лицензию Aegisub исходного проекта тоже не проверял.
- Подтверждения для Buzz (PyQt) и noScribe Editor (PySide) именно по документации не получил.

### Главный вывод для проекта
Данные говорят против ставки на «подсветку по порогу уверенности» как главный механизм: она не ускорила работу и раздражала. Опора лучше на порядок по ожидаемой пользе и стоимости (Sperber), короткие клипы 3–8 слов с контекстом, бинарные «принять / отклонить / пропустить» с клавишами и отменой (Prodigy), выбор из вариантов с возвратом к набору вручную при плохом распознавании (Microsoft, Gaur), и карточки со свайпом, у каждого действия которого есть кнопка (WCAG 2.5.1). Звук нужно запускать только из жеста пользователя и проверять на реальном iPhone.
