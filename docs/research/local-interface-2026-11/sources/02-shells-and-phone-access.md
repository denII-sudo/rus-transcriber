### Задача 1. Способы упаковать интерфейс

#### Сначала три общих факта

1. **Python-ядро на телефоне запускать не нужно и вряд ли получится.** В вашем сценарии телефон только клиент. Но если взять Tauri как оболочку, на iOS и Android в нём нельзя запускать Python как отдельный процесс-sidecar.
   - У плагина `shell` на Android и iOS написано «Only allows to open URLs via `open`» ([Tauri: shell plugin](https://v2.tauri.app/plugin/shell/), прочитано).
   - Страница про sidecar ничего не говорит о мобильных платформах ([Tauri: sidecar](https://v2.tauri.app/develop/sidecar/), прочитано). Единственная найденная жалоба — [issue 9774](https://WWW.GITHUB.COM/tauri-apps/tauri/issues/9774) про Android `os error 2` (только выдержка из поиска, чем закончилось — не видел).
   - На iOS Python работает только встроенным в приложение: нет консоли, исполняемых файлов вне папки Frameworks ([docs.python.org: Python on iOS](https://docs.python.org/using/ios.html), только выдержка из поиска).
2. **Все десктопные оболочки подписываются одинаково.** Подпись нужна, чтобы Windows SmartScreen и Smart App Control не блокировали файл. С 2024 года EV-сертификат не даёт мгновенной репутации ([Tauri: подпись для Windows](https://v2.tauri.app/distribute/sign/windows/), прочитано). Это относится к любой оболочке, не только к Tauri (моё умозаключение).
3. **Подпись Python-ядра, собранного PyInstaller, на macOS хрупкая.** Подписи зависят от путей, а копирование в .app-пакет их ломает; Tauri подписывает sidecar «изнутри наружу» ([ActivityWatch, разбор](https://timetobuildbob.github.io/blog/four-prs-to-sign-one-app), только выдержка из поиска). Про ложные срабатывания антивирусов на PyInstaller и про время холодного старта я источников не нашёл.

#### Что из этого следует (моё умозаключение)

- Для **десктопного окна, трея и уведомлений** разумны три варианта: pywebview (всё на Python, самая малая цена), Tauri (меньше размер, но три движка и Rust) и Electron (одинаковый вид везде, но очень большой).
- Для **телефона отдельное приложение, скорее всего, не нужно**. PWA или обычная вкладка по защищённому адресу решает ту же задачу. Нативный клиент оправдан, только если нужны проверка сертификата вашей локальной службой и отказ от браузерных политик (как у Home Assistant Companion и Immich).
- Flutter, Compose, MAUI и React Native потребуют переписать интерфейс. Для карточки с аудио и кнопками это избыточно.

#### Требования браузеров (проверены по MDN и документации Chrome)

- **Страница по `http://192.168.x.x` не безопасный контекст.** Безопасными считаются только `https`, `localhost`, `*.localhost`, `127.0.0.0/8` и `::1` ([MDN: Secure Contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts), прочитано). Service worker там не зарегистрируется. Из моих знаний (в этой странице списка нет): `getUserMedia` и `navigator.clipboard` тоже требуют безопасного контекста. Перед использованием проверить по [списку MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts/features_restricted_to_secure_contexts).
- **Для воспроизведения клипа по `<audio>` безопасный контекст не нужен** (моё знание, источником не проверял). Для карточки «слушает и отвечает кнопками» нужны только страница, аудио и POST.
- **Cookie с префиксами `__Host-` и `__Secure-` требуют HTTPS** (и атрибута `Secure`), а `SameSite=Strict` работает и по http ([MDN: Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie), прочитано). То есть по http cookie защищена хуже.
- **Chrome с версии 154 (октябрь 2026) по умолчанию спрашивает перед переходом на публичные http-сайты.** Локальные IP, имена из одного слова и «shortlinks» в этом варианте не предупреждают ([Google](https://blog.google/security/https-by-defau/), [Chromium docs](https://chromium.googlesource.com/chromium/src/+show/main/docs/security/ask-before-http/ask-before-http-adoption-guide.md), прочитаны). То есть http по адресу домашней сети предупреждением не станет. Что Chrome 154 действительно вышел в срок — не подтверждено.
- **Local Network Access (LNA) заменила Private Network Access (PNA).** PNA с предварительными запросами отложена и больше не рекомендуется, LNA построена на запросе разрешения у пользователя ([Chrome: LNA](https://developer.chrome.com/blog/local-network-access), прочитано). Chrome 142 включил ограничение по умолчанию 28 октября 2025; в 145 разрешение разделили на `local-network` и `loopback-network`, в 147 добавили WebSocket и WebTransport (сторонние [OpenReplay](https://blog.openreplay.com/chrome-local-network-access-lna-permission/), [Dynamsoft](https://www.dynamsoft.com/web-twain/docs/faq/chromium-142-local-network-access-issue.html), выдержки). Firefox начинает постепенное включение с версии 151 ([Mozilla](https://support.mozilla.org/en-US/kb/control-personal-device-local-network-permissions-firefox), выдержка). Для Safari и мобильных браузеров данных не нашёл.
  **Следствие для вас (моё умозаключение):** LNA касается запросов с публичной страницы к локальному адресу. Страница, которую отдаёт сам локальный сервер, и запросы к нему же под это не подпадают. Разрешение понадобится, только если интерфейс размещён где-то в интернете и обращается к серверу на вашем ПК. Это сильный довод против такой схемы. По странице Chrome разрешения в небезопасном контексте отклоняются автоматически ([Chrome: modern-web-guidance](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access), прочитано).
- **mDNS (`имя.local`).** Браузер передаёт разрешение имён ОС, поэтому работа зависит от версии Android; на старых версиях сообщения «NXDOMAIN». На iOS поддержка заявлена только на форумах ([Home Assistant community](https://community.home-assistant.io/t/detail-mdns-android-os-limitations-on-the-web-server-components-documentation/374099), [Chromium discuss](https://groups.google.com/a/chromium.org/g/chromium-discuss/c/6b0vVreNTvQ), выдержки). На практике запасной вариант — IP-адрес или имя из обычного DNS роутера.
- **mkcert.** Создаёт локальный центр сертификации и ставит его в хранилища ОС; на iOS профиль нужно установить и затем отдельно включить полное доверие; на Android — установить сертификат и (для разработческих сборок) включить пользовательские корни. Файл `rootCA-key.pem` даёт полную власть перехватывать защищённые запросы с машины, поэтому нельзя его копировать. Авторы пишут, что инструмент для разработки, а не для обычных пользователей ([mkcert](https://github.com/FiloSottile/mkcert), прочитано).
- **Tailscale и сертификаты.** Нужно включить MagicDNS и HTTPS-сертификаты; сертификаты выдаёт Let's Encrypt по DNS-01 с TXT-записью `*.ts.net`; закрытый ключ остаётся у вас. Имена машин публикуются в публичном реестре Certificate Transparency, и если они содержат чувствительное — HTTPS не включать. Срок сертификата 90 дней, продлевать самому, если не используется интеграция вроде Caddy ([Tailscale: HTTPS](https://tailscale.com/docs/how-to/set-up-https-certificates), прочитано). Из моих знаний: Tailscale использует облачный сервер координации; в этой странице об этом нет, и вариант с собственным сервером (Headscale) я не исследовал. Для вашего требования «наружу ничего не уходит» это нужно проверить отдельно.

#### Уязвимости и уроки

1. **DNS rebinding против локальных служб.**
   - Ollama CVE-2024-28224, исправлено в v0.1.29: через rebinding атакующая страница читала файлы и управляла моделями. NCC Group советует: TLS везде, аутентификацию на любом сетевом интерфейсе, проверку Host по списку, а не фильтрацию DNS-ответов ([NCC Group](https://www.nccgroup.com/research/technical-advisory-ollama-dns-rebinding-attack-cve-2024-28224/), прочитано).
   - **Август 2026, NVIDIA NemoClaw.** Ollama пропускает проверку Host, когда привязан не к loopback. Если запускать с `0.0.0.0`, rebinding снова работает. Исправлено в NemoClaw 0.0.35 для macOS и Linux, на Windows и WSL — нет; CVE не присвоен ([The Hacker News](https://thehackernews.com/2026/08/a-malicious-webpage-could-poison-your.html), прочитано). Это самый важный урок для вас: **при переходе с 127.0.0.1 на адрес сети проверка Host не должна отключаться.** Syncthing устроен так же («when bound to localhost»).
   - Прочие примеры (только выдержки): SillyTavern (нет проверки Host до 1.13.4), Glances CVE-2026-32632, Deluge ([GitHub Security Lab](https://securitylab.github.com/advisories/GHSL-2024-188_GHSL-2024-191_Deluge)). Одна Host-проверка не защищает от CSRF между сайтами, нужен ещё список разрешённых Origin.
2. **Проверка Origin регулярным выражением.** Jupyter Server до 2.17.0 сопоставлял Origin через `re.match()` (CVE-2026-40110 и CVE-2026-6657, исправлено в 2.18.0; [Red Hat](https://access.redhat.com/security/cve/CVE-2026-40110), только выдержка; страницу NVD открыть не удалось). Урок: сравнивать Origin точно, а не по шаблону.
3. **`Origin: null`** — ComfyUI CVE-2026-6589 (см. таблицу выше). Нужно явно отвергать.
4. **Защиты по GitHub:** TLS (сертификат не совпадёт после rebinding), сильная аутентификация, проверка Host, плюс браузерные меры вроде LNA, которые не дают полной защиты ([GitHub Blog](https://github.blog/security/application-security/dns-rebinding-attacks-explained-the-lookup-is-coming-from-inside-the-house/), прочитано).
5. **Токен в URL** (модель Jupyter). Почему это опасно: попадает в историю браузера и журналы, может утечь через Referer (моё умозаключение, источник не искал).
6. **Брандмауэр Windows** спрашивает при первом запуске слушающей программы и может применить разрешение к частной и публичной сети; разумный вариант — разрешить только «Частная» ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/4236093/defender-firewall-and-python), выдержка).

### Схемы доступа с телефона: от простой к защищённой

| № | Схема | Риски | Что требуется от человека |
|---|---|---|---|
| 0 | Сейчас: `127.0.0.1`, секретный адрес | Телефон недоступен. Остаётся риск rebinding и CSRF на самом ПК, если не проверяются Host и Origin. | Ничего. |
| 1 | `0.0.0.0` или адрес сети + секретный адрес по http | Весь трафик в открытом виде для любого в сети. Токен в истории и логах. Любой в Wi-Fi может перебирать адрес. Rebinding, если Host не проверяется (урок NemoClaw). Нет безопасного контекста: ни service worker, ни PWA. | Разрешить в брандмауэре. Доверять всем в сети. |
| 2 | Схема 1 + проверка Host и Origin, токен меняется на cookie, **сопряжение по QR и одноразовому коду** | Остаётся прослушивание http в Wi-Fi: cookie можно перехватить. | Включить режим сопряжения на ПК, отсканировать QR, подтвердить код на ПК. |
| 3 | Схема 2 + отдельный токен на устройство, срок жизни, список устройств с отзывом, ограничение попыток, ограничение маршрутов | Сопряжённый телефон остаётся ключом: украденный телефон — доступ до отзыва. | Иногда отзывать устройства. |
| 4 | HTTPS с самоподписанным сертификатом и **сверкой отпечатка** при сопряжении (как у Syncthing, KDE Connect, LocalSend) | Браузер показывает предупреждение, и человек привыкает нажимать «продолжить». Работает ли service worker при исключении из предупреждения — не проверял (из моих знаний, что регистрация не проходит; не проверено). LocalSend для браузера вообще откатывается на http. | Нажимать через предупреждение и сверять отпечаток. |
| 5 | Свой локальный центр сертификации (способ mkcert), корень установлен на телефон | Ключ центра сертификации — «полная власть» над перехватом; кража ключа ведёт к подмене любых сайтов на телефоне. Установка корня на iOS в два шага. Тяжело для обычного человека. | Установить профиль на каждый телефон, хранить ключ только на ПК. |
| 6 | VPN (Tailscale, WireGuard) + при необходимости настоящий сертификат `*.ts.net` | Зависимость от внешнего координатора и аккаунта (Tailscale); имена в публичном реестре CT; ставить VPN-клиент на телефон. Простой WireGuard без HTTPS безопасного контекста всё равно не даёт (Open WebUI). | Установить VPN на оба устройства; для Tailscale завести аккаунт. |
| 7 | Нативное приложение-клиент со сверкой сертификата вашей службы | Самая высокая цена: подпись, сборки, магазины. Платит только тот, кому нужны push и офлайн. | Установить приложение. |

Схемы 6 и 7 надёжнее остальных, но 6 нарушает «ничего не уходит наружу» в мягком виде: идёт контакт с внешним координатором и запись в CT.

### Рекомендуемый минимум, если разрешить доступ с телефона в домашней сети

Это моя рекомендация по результатам исследования. Прямого образца для данных вроде ваших в найденных источниках нет.

1. **Выключено по умолчанию.** Включает человек явно и на время (режим сопряжения, как у KDE Connect и Jellyfin Quick Connect). Подтверждение на экране ПК, как уже сделано у вас для опасных действий. Слушать лучше конкретный сетевой адрес, не `0.0.0.0` (моё умозаключение).
2. **Отдельная узкая поверхность для телефона.** Только маршруты карточек: получить карточку, получить клип, отправить ответ. Не открывать управление записями, экспорт, удаление, биометрию. Обосновано политикой ComfyUI: в сети достаточно любого запроса, а авторизации у большинства служб нет.
3. **Проверка Host по точному списку** (адрес сети, выбранное имя, localhost) **и проверка Origin точным сравнением** (без регулярных выражений, `null` отвергать). Не отключать их при привязке к сети: именно это стало уязвимостью NemoClaw. Без CORS «*».
4. **Сопряжение по QR + одноразовый код** с коротким сроком и однократным использованием, подтверждением на ПК. После этого токен переносится в cookie (`HttpOnly`, `SameSite=Strict`, `Secure`, если есть TLS), в адресе его не оставлять. Токен на каждое устройство, список устройств, отзыв, ограничение попыток по образцу Home Assistant.
5. **Клипы с ограниченными правами:** подписанные ссылки на конкретную карточку и короткий срок; никаких путей к файлам в ответах; `Cache-Control: no-store`.
6. **TLS как минимум «желательно».** Для данных с биометрией и разговорами голый http в общей сети я бы считал допустимым только как временный шаг на доверенном домашнем сегменте. Разумные уровни: схема 4 (сверка отпечатка) или 5 (свой центр сертификации). Схема 6 — если вас устраивает внешний координатор.
7. **Сеть:** правило брандмауэра Windows только для программы и только для профиля «Частная»; отключить доступ гостевой сети к ПК; не пробрасывать порты на роутере; проверить, нет ли доступа по IPv6 из внешней сети (последние два — моё умозаключение).
8. **Журнал сопряжений и отзывов, остановка сервера по таймеру.**
