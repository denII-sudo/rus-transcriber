1. ЧТО ЭТО ПРОСТЫМИ СЛОВАМИ
- Node.js: программа, которая запускает JavaScript вне браузера. Для самого интерфейса она не нужна. Она нужна инструментам разработчика.
- npm (и родственные pnpm, yarn): «магазин» готовых кусочков кода. Он скачивает библиотеки (React, Svelte и сотни их подпорок) в папку node_modules.
- Сборка (bundling): Vite или esbuild склеивают сотни исходных файлов в несколько маленьких. При этом переводят «удобный» код (TypeScript, JSX, Svelte) в обычный JavaScript, который понимает браузер.
- На выходе получается папка из HTML, JS и CSS. Её отдаёт ваш Python-сервер, как сейчас отдаёт ваши страницы.
- Кому что нужно:
  - Разработчик (агент) ставит Node и зависимости.
  - CI (проверка на GitHub) ставит Node и собирает.
  - Пользователь получает уже собранную папку, Node ему не нужен. Это ключевой принцип.
  - Исключение: установка из Git-клона. Там собранных файлов нет, пока их не положили в репозиторий или в релиз.

2. КАК ЭТО ДЕЛАЮТ ИЗВЕСТНЫЕ ПРОЕКТЫ
- JupyterLab [Д]: готовые расширения, по документации, ставятся «без Node.js», и рекомендуют публиковать их в Python-пакетах. Расширения из исходников требуют Node и пересборки, и этот путь признан устаревшим. https://jupyterlab.readthedocs.io/en/stable/extension/extension_dev.html
- Home Assistant [Д]: интерфейс вынесен в отдельный пакет `home-assistant-frontend` на PyPI. Это «чистое» колесо (wheel), собранное в GitHub Actions и опубликованное через Trusted Publishing. Размер колеса вырос с примерно 46 МБ (2023) до примерно 124 МБ (2026). https://pypi.org/project/home-assistant-frontend/20260729.4/
- MLflow [Д]: папка `build` не лежит в Git. Её создают командой `yarn build`, а затем `python -m build` собирает колесо. https://raw.githubusercontent.com/mlflow/mlflow/master/CONTRIBUTING.md
- Streamlit [Д]: для разработки нужны Node (версия записана в `.nvmrc`) и yarn через Corepack. Как именно фронтенд попадает в колесо, я не подтвердил. https://raw.githubusercontent.com/streamlit/streamlit/develop/CONTRIBUTING.md
- Gradio [Д]: фронтенд собирается скриптом `build_frontend.sh` на pnpm. Известна поломка из-за нехватки памяти Node, лечится `--max_old_space_size=8192`. https://raw.githubusercontent.com/gradio-app/gradio/main/CONTRIBUTING.md
- Open WebUI [Д]: SvelteKit + Vite, нужен Node 20.19+ или 22.13+. Сборка идёт с лимитом памяти 12 ГБ. Устройство pip-пакета я не проверил. https://docs.openwebui.com/getting-started/advanced-topics/development
- Paperless-ngx [Д]: Angular, фронтенд собирается на отдельной стадии Dockerfile. Пользователь получает готовый образ. https://www.Github.com/paperless-ngx/paperless-ngx/blob/dev/Dockerfile
- Label Studio [Д]: собранные файлы лежат в `site-packages/label_studio/frontend/dist/`, то есть внутри пакета. https://labelstud.io/guide/frontend
- pgAdmin, NiceGUI, Django admin: подтверждающих источников я не нашёл.
- Datasette [Ф/Д]: без сборки. Автор прямо говорит, что не любит локальные скрипты сборки. Плагины включают JS-зависимости в сам пакет, а для интерактива есть готовый Preact (`datasette-preact`). Поддержка ES-модулей есть с версии 0.54. https://simonwillison.net/2023/May/2/download-esm/
- 37signals/Rails importmap [Д]: библиотеки скачиваются в `vendor/javascript` и коммитятся в Git. Ограничение: библиотеки должны быть уже готовыми ES-модулями, про TypeScript и JSX документация молчит. https://github.com/rails/importmap-rails

Где лежит результат сборки (плюсы и минусы):
- В Git. Плюсы: установка из клона работает сразу, Node не нужен пользователю. Минусы: шум в диффах, риск рассинхрона исходников и сборки; лечится проверкой в CI («пересобрали, ничего не изменилось»).
- В релизе или колесе PyPI. Плюсы: Git чистый, так делают Jupyter, Home Assistant, MLflow. Минусы: установка прямо из клона без Node не даёт интерфейса. Нужен отдельный путь «скачать собранное».
- Только в Docker-образе. Это не подходит вашему сценарию «скрипт ставит из Git».

3. ЦЕНА ВЛАДЕНИЯ
- Частота поломок:
  - Vite 8 вышел 12.03.2026 (на Rolldown) и требует Node 20.19+ или 22.12+. [Д] https://vite.dev/blog/announcing-vite8
  - Mantine 9 (май 2026) требует React 19.2+ и ломает API (`Text color`, схемы форм). [Д] https://mantine.dev/guides/8x-to-9x
  - TypeScript 7 (на Go) вышел 08.07.2026. Для Svelte и Vue инструменты пока остаются на TS 6. [Д] https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/
  - [?] Крупный пересмотр у экосистемы примерно раз в 6–12 месяцев. Для проекта, который ведут агенты, это постоянная работа с Dependabot.
- Объём: Contexte при уходе с React на htmx сократил число JS-зависимостей с 255 до 9, а сборку с 40 до 5 секунд (2022). Но это контентное приложение, и автор htmx сам оговаривает, что такой выигрыш типичен не для всех. [Д] https://htmx.org/essays/a-real-world-react-to-htmx-port/
- Типичные поломки: нехватка памяти при сборке (Gradio, Open WebUI), несовместимость версии Node, конфликты peer-зависимостей (`npm install --force` у Open WebUI).
- Обратные истории:
  - Gumroad (30.09.2024) отказался от htmx в пользу React/Next.js. Причины: сложные формы, drag-and-drop, состояние, нехватка готовых библиотек, а ИИ лучше знает Next.js. [Д] https://four.htmx.org/essays/why-gumroad-didnt-choose-htmx
  - [Ф] В одном кейсе 2025 года дерево с перетаскиванием осталось на React даже после перехода на htmx.
  - Письменных «пожалели о сборке» я не нашёл.

4. ЦЕПОЧКА ПОСТАВОК npm (2025–2026)
- Shai-Hulud (первая волна, 14–15.09.2025): червь через `postinstall`. Он крал токены, перепубликовал пакеты автора с вредом и затронул 180+ пакетов. [Ф] https://www.darkreading.com/application-security/self-replicating-shai-hulud-worm-npm-packages
- Shai-Hulud 2.0 (21–24.11.2025): около 700–800 пакетов, 25 тыс. репозиториев GitHub с утечками; использовал `preinstall` и Bun. Если сбой, чистил домашнюю папку. [Ф] https://www.theregister.com/2025/11/24/shai_hulud_npm_worm/
- axios (31.03.2026): угнали аккаунт сопровождающего, версии 1.14.1 и 0.30.4 принесли троян через зависимость `plain-crypto-js`. Обнаружил сканер Socket за 6 минут. [Ф] https://www.malwarebytes.com/blog/news/2026/03/axios-supply-chain-attack-chops-away-at-npm-trust
- «Mini Shai-Hulud» / ChainDrop (Microsoft, 04.08.2026): 400+ пакетов; вредоносные версии с действительной provenance через OIDC; также записывал конфиги Claude и VS Code в репозитории жертв. [Д] https://microsoft.com/en-us/security/blog/2026/08/04/chaindrop-supply-chain-compromise-anatomy-self-propagating-worm
- Защита (суть: три слоя) [Д] https://pnpm.io/supply-chain-security
  1. Lock-файл плюс `npm ci` или `pnpm install --frozen-lockfile`.
  2. Запрет скриптов установки. В pnpm 10+ они выключены по умолчанию, список разрешённых задаётся через `allowBuilds`. В npm работает `ignore-scripts=true`.
  3. «Остывание» версий: `minimumReleaseAge` в pnpm (по умолчанию 1440 минут, добавлено в 10.16). В npm аналог `min-release-age` с версии 11.10 (по одному из источников).
  Дополнительно: `blockExoticSubdeps`, `trustPolicy: no-downgrade`, закрепление GitHub Actions по SHA, минимальные права токена. Источник перечня: https://dev.to/trknhr/lessons-from-the-spring-2026-oss-incidents-hardening-npm-pnpm-and-github-actions-against-1jnp
- Реалистично ли для маленького проекта [?]: да, но риск в основном у машины разработчика и CI, а не у пользователя (получает готовые файлы). Главное: сборка в изолированном CI без секретов, а не на личном компьютере с токенами. Это сильный довод в пользу схем, где у пользователя Node нет вообще.

5. АЛЬТЕРНАТИВЫ NODE
а) Bun и Deno [Ф]: по обзорам, годятся для продакшена. Самая распространённая схема: Bun только для установки и скриптов, а сборку делает Vite. Данные про Windows противоречивы (Bun для Windows x64 стабилен с 1.1). Выигрыш для вас небольшой, а Bun сам использовался червём.
б) Сборщик без Node:
- esbuild: нативный бинарник. Собирает TypeScript и JSX, плагины недоступны. Но он не проверяет типы. Скачать можно из npm-реестра как tar без самого npm, а скрипт `curl | sh` только для Unix. [Д] https://esbuild.github.io/getting-started/
- Tailwind standalone CLI: работает без Node. [Д] https://tailwindcss.com/blog/standalone-cli
- [?] React/Preact + TypeScript без Node собрать можно (esbuild), но проверка типов (`tsc`) всё равно потребует Node/npm. TS 7 нативный, но ставится через npm. Отдельного бинарника я не нашёл.
в) Вообще без сборки:
- ES-модули, import map, Preact+htm (вместо JSX), htmx, Alpine, Lit. [Д] https://preactjs.com/guide/v10/no-build-workflows
- Особенность Preact: два экземпляра библиотеки дают трудноуловимые ошибки. Локальные копии лежат в репозитории, как в Rails importmap.
- Теряете: JSX, готовые React-библиотеки, часть типизации.
- Типы через JSDoc плюс `tsc --checkJs`: по моему знанию это работает, но подтверждающего источника в поиске не нашлось [?].
г) Node через pip:
- `nodejs-wheel` и `nodejs-wheel-binaries` на PyPI, это неофициальные колёса. Они дают `node`, `npm`, `npx` и Corepack. Поддерживаются Windows amd64, Linux, macOS, доступна Trusted Publishing. [Д] https://pypi.org/project/nodejs-wheel
- Подходит для разработчика и CI, но Node в колесе от стороннего автора добавляет ещё одно доверенное звено.
- django-vite и PyScript: [?] django-vite всё равно требует Node для сборки, PyScript для вашей задачи не подходит.

6. ТЕСТИРОВАНИЕ ИНТЕРФЕЙСА
- Playwright для Python: колесо содержит встроенный Node-драйвер. Отдельно ставить Node не нужно, браузеры скачивает `playwright install --with-deps`. Через `pytest-playwright` есть эмуляция телефона по профилям устройств. Колёса зависят от платформы. [Ф/Д] https://playwright.dev/python/docs/emulation
- Эмуляция телефона: десктопный Chromium с размером экрана и касаниями, не реальный телефон.
- GitHub Actions: стандартные раннеры бесплатны для публичных репозиториев. В 2026 это сохранено, платными остаются только «большие» раннеры. Windows, Linux и macOS доступны. [Д] https://docs.github.com/en/billing/concepts/product-billing/github-actions
- Vitest и Testing Library нужны только при сборке на Node. Для схемы без Node их заменяет Playwright на Python.

7. ИИ-АГЕНТЫ И ВЫБОР СТЕКА
- Данных нет, чтобы сказать «X надёжнее Y». Бенчмарки Web-Bench и DesignBench тестируют React, Vue, Angular и обычный HTML, но не htmx и почти не Svelte. [Д] https://arxiv.org/pdf/2505.07473
- Фактическое: у React больше всего обучающих данных (Web-Bench). Модели хуже справляются с фреймворками, чем с простым HTML (DesignBench). [Д] https://arxiv.org/html/2506.06251v3
- Svelte 5: модели путают руны; у Svelte есть официальный MCP и `llms.txt`, но независимых цифр «с MCP и без» я не нашёл. https://svelte.dev/docs/ai
- Gumroad называл слабое знание htmx моделями причиной ухода (2024).
- Типы: один небольшой тест (по 15 запусков) показал, что React-запуски часто ломали типы (6 из 15), а Angular нет. Автор сам называет это возможной случайностью. [Ф] https://www.aihero.dev/essential-ai-coding-feedback-loops-for-type-script-projects
- Playwright MCP даёт агенту живой браузер, но в одном сравнении не улучшил результат (80% против 70% выполненных критериев без него) и стоил на 17% дороже. [Ф]
- Прямых отзывов о «чистом JS без сборки» для Claude не нашёл. Что помогает [?]: типы, линтер, браузерные тесты на Playwright.

8. ИТОГ: ТРИ СХЕМЫ
Схема А. Без сборки (ES-модули + Preact/htm или htmx + локальные копии библиотек в Git + Playwright для Python).
- Цена: у разработчика и пользователя Node нет. Установка из Git-клона работает сразу. Риск цепочки поставок минимален. Теряете JSX, готовые React-компоненты и строгую типизацию (частично возвращается через JSDoc).
- Подходит при: 3–6 экранах, интерфейс в основном карточки и чтение, сопровождают агенты.
Схема Б. Сборка в CI, результат в репозитории или релизе.
- Устройство: исходники на Vite или esbuild + TypeScript, Node только у разработчика и в CI, пользователь получает готовые файлы. Лежат они в Git (проверка «собранное = исходникам» в CI) или в релизе.
- Цена: нужен Node (через nodejs-wheel или обычный), pnpm с минимальным возрастом версий, `ignore-scripts`, Dependabot. Нужен ещё путь для установки из клона: скрипт скачивает собранное из релиза.
- Подходит при: 6–15 экранах и сложных клавишах, жестах, плеере.
Схема В. Полная сборка в пакете (как Home Assistant, Jupyter).
- Устройство: отдельный пакет с интерфейсом, публикация через Trusted Publishing, версии согласуются с сервером.
- Цена: самая высокая. Нужны релизный процесс, версионирование, поддержка зависимостей.
- Подходит при: больших командах и десятках экранов. [?] Для вашего проекта это избыточно.

Критерии выбора: число экранов; насколько много состояния в одном экране (стенограмма + плеер + жесты) и нужны ли перетаскивание и сложные формы (это слабое место htmx по Gumroad); нужны ли готовые React-библиотеки; кто сопровождает (агентов выручают типы и тесты); важна ли установка из клона без дополнительных скачиваний.

Моё предварительное мнение [?]: начать со схемы А с типами через JSDoc и Playwright на Python. К схеме Б переходить только после реального упора в сложность состояния. Подпорка для такого решения: для вашего круга пользователей-неспециалистов главным достоинством остаётся отсутствие Node на их стороне.

НЕ ПОДТВЕРЖДЕНО: устройство колёс Streamlit и Open WebUI; данные по pgAdmin, NiceGUI, Django admin; работа `checkJs`; отдельный бинарник TS 7; точная частота ломающих обновлений React и Svelte; опыт «пожалели об отсутствии сборки». Многие цифры 2026 года взяты из блогов, их стоит сверить с первоисточником.
