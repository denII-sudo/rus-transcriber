## 1. Кратко

Проверено около 35 рабочих модулей (примерно 20 тыс. строк). Основная логика
расшифровки, хранения, разбора, голосовых профилей и подтверждений выглядит
продуманной: есть блокировки, атомарная запись во многих местах, проверки ревизий
и контрольные суммы архивов. Но найдены несколько мест, где защита есть только в
SQLite-режиме и не действует в режиме по умолчанию `legacy_files`, а также места,
где идентификатор из MCP-вызова попадает в путь к файлу без проверки.

| Уровень | Сколько | Коротко |
| --- | ---: | --- |
| **Критично** | 1 | `job_id` без проверки попадает в путь: чтение/перезапись `.json`, завершение процесса по `.pid` |
| **Высоко** | 4 | Обход границы «человек/модель» в legacy-режиме; `confirm_mode=off` для действий, требующих человека; потеря ответов при конкурентной записи; путь из `item_id` при записи WAV |
| **Средне** | 11 | Состояние отменённой задачи; имена групп; атомарность импорта и настроек; бесконечная блокировка голосов; сообщение миграции; bidi-символы в окне подтверждения; `drop_audio` в SQLite; очистка живых задач; зарезервированные имена Windows |
| **Низко** | 6 | Типы в `config.json`; очистка `TEMP`; изоляция тестов; гонка порта OpenCode; временный файл подтверждений; потеря PID при запуске |

Второй проход добавил 7 находок: 4 средних (**M12–M15**) и 3 низких (**L7–L9**).
Итог по двум проходам: **29 находок** — 1 критично, 4 высоко, 15 средне, 9 низко.
Оценки части 1 не пересматривались; часть 2 лежит в разделе 12.

Главный вывод: продукт в целом следует правилу «человек > голосовой профиль >
распознавание», но в обычном режиме `legacy_files` некоторые проверки, которые
явно написаны для SQLite, не выполняются. Это не косметика, а нарушение
авторства правок и доверия к голосовым профилям. Второй проход подтвердил
соседние риски обычного режима: сохранение стенограммы и пакетное применение
ответов неатомарны, а PID-файлы не связаны с конкретным процессом.

## 2. Как читать отчёт

- **Критично** — действие через обычный MCP-инструмент может затронуть файлы или
  процессы за пределами задачи; нужен срочный запрет/проверка.
- **Высоко** — нарушение границы «человек/модель» или потеря человеческих данных
  в нормальном сценарии; исправлять до следующей приёмки.
- **Средне** — порча данных, согласия или состояния при определённых условиях
  (конкурентная запись, сбой, необычное имя); исправлять планово.
- **Низко** — устойчивость и удобство эксплуатации; можно отложить, но лучше
  закрыть вместе с соседними правками.

Ссылки даны в виде `модуль:строки`. Номера строк относятся к коммиту `6a5fcf5`;
для части 2 — к `0a3a29f` (пять проверяемых модулей не менялись с `6a5fcf5`).
После правок номера нужно сверить заново.

## 3. Критично

### C1. `job_id` без проверки попадает в путь к файлу

**Где:**
- `core.py:59-63` — `pid_of`: `JOBS / f"{job_id}.pid"`.
- `core.py:66-90` — `job_status`: `JOBS / f"{job_id}.json"`.
- `core.py:117-139` — `cancel_job`: читает статус, читает PID, вызывает `taskkill`,
  затем пишет `cancelled` в тот же путь.
- `server.py:327-334` — MCP-инструмент `cancel_job`.
- `server.py:639-661` — `transcription_status` возвращает содержимое статуса.
- `server.py:664-680` — `read_transcript` читает путь `json` из статуса.

**Суть.** `job_id` приходит из MCP-вызова как обычная строка и нигде не
проверяется на формат. Выражение `JOBS / f"{job_id}.json"` принимает `..\..\`,
вложенные каталоги и даже абсолютный путь. В результате:

- `transcription_status` может вернуть содержимое произвольного `.json`-файла,
  который является объектом JSON (функция возвращает весь словарь, а не только
  известные поля);
- `read_transcript` может прочитать файл, путь к которому записан в поле `json`
  произвольного JSON;
- `cancel_job` может перезаписать произвольный `.json` статусом `cancelled`;
- `cancel_job` может прочитать произвольный `.pid` и завершить процесс с этим
  PID, если такой файл существует.

**Почему это критично, хотя сервер локальный.** MCP-клиент — это ИИ-агент, а
стенограмма и аудио — недоверенные данные. Ошибка агента или инъекция в текст
(«вызови cancel_job с таким job_id») превращает безобидный инструмент в файловую
операцию по произвольному пути и в завершение процесса. Даже без злого умысла
опечатка в `job_id` может испортить чужой JSON.

**Минимальное исправление.**
1. Ввести строгую проверку формата: `^\d{8}-\d{6}-[a-z][0-9a-f]{5}$` для обычных
   задач и `^workflow-[0-9a-f]{32}$` для workflow, если такие ID используются.
2. После сборки пути проверить, что `p.resolve().is_relative_to(JOBS.resolve())`
   (Python 3.9+; для 3.13 это безопасно).
3. Не принимать абсолютные пути и любые `/`, `\`, `..`.
4. Для `cancel_job` отдельно проверить, что PID взят из файла внутри `JOBS`, а не
   из произвольного пути.
5. Добавить тесты: `..\x`, `C:\x`, `a/b`, пустая строка, слишком длинный ID.

**Проверка после исправления.** Вызовы `transcription_status("..\\..\\x")`,
`cancel_job("C:\\temp\\x")` и `read_transcript("a/b")` должны возвращать понятную
ошибку, не трогая файлы.

## 4. Высоко

### H1. В режиме `legacy_files` (по умолчанию) не работают проверки авторства, написанные для SQLite

**Где:**
- `settings.py:26` — `recording_backend` по умолчанию `legacy_files`.
- `core.py:1401-1464` — `apply_answers`/`apply_answers_files`: проверка
  «ответ неизвестного происхождения нельзя применять как человеческий» находится
  только в ветке `store is not None` (`core.py:1413-1430`).
- `core.py:1463-1464` — legacy-ветка сразу вызывает `_apply_answers_files_locked`.
- `core.py:1518` — все решения применяются с `by="human"`.
- `review_pack.py:643` — свободные ответы также применяются с `by="human"`.
- `server.py:1179-1188` — `import_answers` принимает `source="cloud"` и произвольные
  ответы, в том числе с `audio`.
- `server.py:446-447` — `rename_speakers` в legacy-режиме сразу выполняет
  переименование без подтверждения и проверки имён.
- `server.py:500-507` — `edit_span(by="human")` запрещён только при наличии
  SQLite-записи; в legacy-режиме параметр принимается как есть.
- `core.py:1589-1592` — `edit_span` передаёт `by` в `transcript.edit_span`.
- `transcript.py:27` — `by="human"` превращается в `actor_kind="human"`.
- `transcript.py:416-417` — `transcript.rename` ставит `names_confirmed=True` и
  `names_source="rename"`.
- `transcript.py:779-780`, `812-820` — слова с `by="human"` защищены от будущих
  модельных правок.

**Суть.** В SQLite-ветке явно проверяется происхождение ответов и запрещается
применять ответы неизвестного происхождения как человеческие. В legacy-ветке
такой проверки нет: `apply_answers` применяет всё, что лежит в `answers.json`, с
меткой `human`. Аналогично `edit_span` верит параметру `by="human"`, а
`rename_speakers` без подтверждения ставит `names_confirmed=True`.

**Последствия.**
- Модель или облачный ответ, импортированный через `import_answers`, может стать
  «человеческой» правкой, получить защиту от последующих правок и повышенный вес
  при обучении голосового профиля.
- ИИ-агент может переименовать говорящих и тем самым «подтвердить» имена для
  голосового профиля без человека.
- ИИ-агент может пометить свой текст как `human`, и система будет считать его
  человеческим при разборе и обучении.
- Это прямо противоречит правилу «человек > голосовой профиль > распознавание» и
  обесценивает журнал авторства.

**Минимальное исправление.**
1. Ввести явный параметр `trusted_actor`/`actor_kind` для
   `core.apply_answers_files`, `core.edit_span` и `core.rename_speakers`.
2. Для MCP-вызовов всегда считать actor `model`/`unknown`, никогда `human`.
3. Для `by="human"` и `rename_speakers` в legacy-режиме требовать
   `confirm.require(...)` с реальным человеком (или вообще запретить эти
   операции через MCP, как уже сделано для SQLite).
4. Проверку происхождения ответов вынести в общую функцию и вызывать в обеих
   ветках, а не только при `store is not None`.
5. Добавить тесты: legacy + `import_answers(source="cloud")` + `apply_answers`
   должен отказать или оставить ответ человеку; `edit_span(by="human")` через MCP
   в legacy должен требовать подтверждения; `rename_speakers` в legacy должен
   требовать подтверждения.

### H2. Действия, которые по смыслу требуют человека, проходят при `confirm_mode=off`

**Где (вызовы без `require_human=True`):**
- `server.py:605` — `conspect_mark_reviewed`: подтверждение проверки конспекта.
- `server.py:634` — `conspect_link_selected`: выбор мест цитат человеком.
- `server.py:748` — `request_review_answer_verification`: подтверждение ответов
  неизвестного происхождения.
- `server.py:779`, `server.py:800` — разрешение конфликтов документа/конспекта.
- `server.py:870` — `export_group`: выгрузка биометрии.
- `server.py:884` — `import_group`: импорт/замена голосовых профилей.
- `server.py:899` — `delete_group`: удаление группы с биометрией.
- `server.py:1036`, `server.py:1049` — обновление/отзыв голосового профиля.
- `server.py:1103` — резервное копирование голосовых профилей.
- `server.py:1139` — `resolve_voice`: решение по тёзке; здесь вызывается
  `confirm.require` напрямую, а не через `_gated`.

**Где записывается «human»:**
- `core.py:1359` — `confirm_conspect_analysis` пишет `operation_for_document(..., "human")`.
- `core.py:966` — `confirm_review_answers` пишет человеческий контекст.
- `core.py:1021`, `core.py:1043` — разрешение конфликтов пишет
  `operation_context(store, "human")`.
- `server.py:1139-1150` — решение `resolve_voice` сохраняется в профиль.

**Контраст с правильным поведением:**
- `server.py:190-199` — `workflow_abandon_request` явно запрещает `off`.
- `server.py:207-217` — `workflow_mark_reviewed` явно запрещает `off`.
- `server.py:301-312` — `restore_recording_revision` явно запрещает `off`.

**Суть.** `_gated(..., require_human=False)` по умолчанию принимает любой способ
подтверждения, включая `off`. В результате при `confirm_mode=off` система без
человека записывает «человек подтвердил», выгружает/удаляет биометрию и меняет
голосовые профили. Это не просто отсутствие окна: в журналах и Snapshot-ах
появляется человеческое авторство, которого не было.

**Последствия.**
- Ложное «human»-подтверждение конспекта или ответов разбора.
- Выгрузка или удаление биометрии без согласия человека.
- Решение по тёзке и изменение профиля без человека.
- Невозможно отличить реальную проверку от автоматического прогона.

**Минимальное исправление.**
1. Для перечисленных действий передать `require_human=True` в `_gated`.
2. Для `resolve_voice` добавить проверку `confirm.mode() != "off"` до
   `confirm.require` (или обернуть в общий помощник).
3. Для действий с биометрией (`export_group`, `import_group`, `delete_group`,
   `update_voice_profiles`, `revoke_voice_profiles`, `backup_voice_profiles`)
   явно требовать диалог/терминал, а не `off`.
4. Добавить тест: при `confirm_mode=off` каждый такой инструмент возвращает
   отказ и не меняет файлы/БД.

### H3. Конкурентная запись `answers.json` теряет ответы человека в legacy-режиме

**Где:**
- `review_pack.py:62-72` — `_write` использует фиксированный
  `answers.json.tmp` и не берёт межпроцессную блокировку.
- `review_pack.py:287-292` — `_write_answers` вызывает `_write` для legacy.
- `review_pack.py:381-386` — `add_answers` делает read-modify-write.
- `review_page.py:47` — блокировка `threading.Lock` действует только внутри
  процесса страницы.
- `review_page.py:133-163` — под этой блокировкой идут ответы страницы.
- MCP-инструмент `import_answers` (`server.py:1179-1188`) работает в другом
  процессе и эту блокировку не видит.

**Суть.** Человек отвечает на локальной странице, а ИИ-агент в это же время
импортирует облачные ответы через MCP. Оба процесса читают один `answers.json`,
оба пишут во временный `answers.json.tmp`, затем заменяют файл. Один набор
ответов может быть потерян; при совпадении записей временный файл может быть
частично перезаписан и стать невалидным JSON. В SQLite-режиме есть проверка
ревизий и `Conflict`, но в legacy-режиме (по умолчанию) её нет.

**Последствия.** Потеря человеческих ответов, конфликт «ответ был, но пропал»,
невозможность восстановить, какой ответ победил. Для продукта, где ответы
человека — главный источник истины, это высокий риск.

**Минимальное исправление.**
1. Использовать уникальное имя временного файла
   (`tempfile.NamedTemporaryFile(dir=..., delete=False)`) и `os.replace`.
2. Взять межпроцессную блокировку на время read-modify-write. В проекте уже есть
   `jobslots._try_lock` и `settings.group_voice_lock`; можно сделать общий
   файловый lock рядом с `answers.json`.
3. В `review_page` и `review_pack` использовать один и тот же lock, а не только
   `threading.Lock`.
4. Добавить тест с двумя процессами/потоками, которые добавляют разные ответы;
   после завершения оба ответа должны быть в файле.

### H4. `item_id` без проверки попадает в имя WAV при включённом `review_local`

**Где:**
- `server.py:1230-1240` — `_listen_reply`:
  `wav = folder / f"{item_id or 'reply'}-listen-{int(time.time())}.wav"`.
- `voice_io.py:135-150` — `record` делает `Path(path).resolve()`, создаёт
  родительские каталоги и пишет WAV.
- `server.py:1270-1274` — инструмент `listen_reply` доступен только при
  `review_local` (декоратор `_local_voice_tool`, `server.py:913-921`).

**Суть.** `item_id` не проверяется по manifest. Если передать `..\..\evil` или
абсолютный путь, WAV будет записан вне папки пакета; `record` создаст нужные
каталоги. Это запись/перезапись файла с расширением `.wav` по произвольному пути.

**Последствия.** Порча пользовательского файла, запись аудио в неожиданное место,
обход ожидания «всё лежит в папке пакета». Условие: `review_local` включён;
по умолчанию он выключен, поэтому это не критично, но при включении — высокий
риск.

**Минимальное исправление.**
1. Проверить `item_id` по `P.manifest(jp)["items"]`; использовать канонический
   `it["id"]`, а не входную строку.
2. Если `item_id` пустой — использовать фиксированное `reply`.
3. После сборки пути проверить, что он внутри `folder` (resolve + is_relative_to).
4. Добавить тест: `item_id="..\\x"` и `item_id="C:\\x"` отклоняются, файл не
   создаётся.

## 5. Средне

### M1. Нет ограничений на пути чтения конспекта и аудио для распознавания

**Где:**
- `server.py:552` — `check_quotes` читает любой `conspect_path` через
  `Path(...).read_text`.
- `server.py:1179-1188` — `import_answers` принимает `audio` как произвольный путь.
- `review_pack.py:400-405` — `recognize_files` распознаёт все переданные файлы.

**Суть.** Оба инструмента по дизайну принимают путь «на этом компьютере», но не
ограничивают корень, размер и тип файла. ИИ-агент может прочитать текст вне
`DATA_DIR` и вернуть цитаты, а может распознать произвольный аудиофайл и получить
его текст. При недоверенном клиенте или инъекции в стенограмму это канал чтения
локальных данных.

**Минимальное исправление.** Ограничить пути `DATA_DIR`/папкой пакета, проверять
размер и расширение; для облачных ответов запретить `audio`; для внешних путей
требовать явное подтверждение человека.

### M2. `cancel_job` пишет `cancelled`, даже если процесс жив, и неатомарно

**Где:**
- `core.py:117-139` — после `taskkill` не проверяется `alive(pid)` перед записью;
  `killed` может быть `False`, но статус всё равно `cancelled`.
- `core.py:137-138` — статус пишется `write_text` напрямую.
- `worker.py:219-231` — worker пишет статус через временный файл и `os.replace`.

**Суть.** Если `taskkill` не сработал (права, гонка, дочерний процесс), задача
продолжает работу, но интерфейс показывает «отменено». Кроме того, `cancel_job`
может перезаписать уже завершённую задачу: между `_need` и записью worker успеет
записать `done`. Прямая запись неатомарна и может пересечься с записью worker.

**Минимальное исправление.** После ожидания проверить `alive(pid)`; если процесс
жив — вернуть ошибку и не менять статус. Перед записью перечитать статус и не
перезаписывать `done`/`error`. Писать через временный файл и `os.replace`.

### M3. Подтверждение и имя группы расходятся при экспорте и удалении

**Где:**
- `data_io.py:84` — `export_data` экспортирует `paths.safe_group(group)`.
- `core.py:2268-2273` — `describe_export` показывает исходное `group`.
- `data_io.py:315-318` — `delete_group` сравнивает `confirm` с исходным `group`,
  но удаляет `safe_group(group)`.
- `core.py:2286-2293` — `describe_delete` показывает уже санитизированное имя.

**Суть.** Для группы `"Моя группа"` диалог экспорта покажет `"Моя группа"`, а
экспортируется `"Моя_группа"`. При удалении подтверждение сравнивается с исходным
именем, а удаляется санитизированное. Человек подтверждает одно имя, операция
касается другого. Для биометрического экспорта это риск согласия.

**Минимальное исправление.** Либо требовать `paths.safe_group(group) == group` на
границе (как в `settings.group_voice_settings`), либо везде использовать одно
санитизированное имя и показывать его в диалоге.

### M4. Импорт пишет словарь неатомарно и без блокировки группы

**Где:**
- `data_io.py:272`, `data_io.py:278` — `vocab.json` пишется `write_bytes`.
- `data_io.py:290`, `data_io.py:307-308` — `voices.json` пишется через
  `_write_json`.
- `data_io.py:170-174` — `_write_json` использует фиксированный
  `voices.json.tmp`.
- `data_io.py:206-311` — импорт не берёт `settings.group_voice_lock`.

**Суть.** При сбое посреди записи словарь может остаться частичным. При
одновременном обновлении голосового профиля импорт и worker пишут один файл без
общей блокировки; фиксированный `.tmp` может столкнуться. В режиме `replace`
резерв копируется, но отката при частичном сбое нет.

**Минимальное исправление.** Обернуть изменения группы в
`settings.group_voice_lock(g)`; писать словарь через уникальный временный файл и
`os.replace`; при ошибке возвращать отчёт о уже выполненных шагах.

### M5. `settings.save_overrides` использует фиксированный `config.tmp` без блокировки

**Где:**
- `settings.py:64-66` — `paths.CONFIG_FILE.with_suffix(".tmp")`.
- `settings.py:70-77` — `update` делает read-modify-write.

**Суть.** Тест скорости, локальная страница и человек могут одновременно менять
`config.json`. Оба пишут один `config.tmp`, затем заменяют файл. Один набор
изменений теряется; возможна ошибка замены.

**Минимальное исправление.** Взять межпроцессную блокировку на время
read-modify-write, использовать уникальный временный файл и `os.replace`.

### M6. `group_voice_lock` ждёт вечно

**Где:** `settings.py:168-179` — `while not jobslots._try_lock(f): time.sleep(0.1)`.

**Суть.** Если процесс, держащий блокировку, завис, обновление профиля,
`resolve_voice` и другие операции ждут бесконечно; MCP-вызов не возвращается.

**Минимальное исправление.** Добавить таймаут (например, 60 с) и понятную ошибку
«профиль занят другим процессом; повторите позже». ОС освобождает файловую
блокировку при завершении процесса, поэтому «вечный» lock обычно означает
зависший живой процесс.

### M7. При сбое миграции сообщение «исходные файлы не тронуты» может быть ложным

**Где:** `migrate.py:184-213` — файлы перемещаются по одному в цикле
`shutil.move`, а в `except` пишется «исходные файлы не тронуты».

**Суть.** Если ошибка произошла после нескольких успешных `move`, часть файлов
уже в резервной копии, а часть — на месте. Сообщение вводит в заблуждение;
повторный запуск не имеет явного плана продолжения.

**Минимальное исправление.** Считать `moved` и писать фактическое состояние
(«перемещено N, проверьте backup»); сохранять маркер/план миграции для
продолжения; сделать повторный запуск идемпотентным.

### M8. Окно подтверждения пропускает bidi/управляющие символы и обрезает строки без пометки

**Где:** `confirm.py:57-64` — `clean` оставляет все символы `>= " "`, включая
U+202E (bidi override), zero-width и часть C1; каждая строка обрезается до 220
символов без «…».

**Суть.** Текст в окне подтверждения — последняя линия защиты. Bidi-символы
могут визуально переставить слова, а обрезка — скрыть хвост условия. Человек
подтверждает не то, что реально будет выполнено.

**Минимальное исправление.** Удалять/заменять категории Unicode `Cc`, `Cf`, `Cs`;
нормализовать текст; добавлять «…» при обрезке строки; ограничивать общую длину
и число строк.

### M9. `drop_audio` не удаляет клипы SQLite-режима

**Где:**
- `review_pack.py:105-107` — в SQLite-режиме клипы лежат в
  `clips/<uuid>/`.
- `review_pack.py:816-824` — `drop_audio` делает `unlink()` для каждого элемента
  `clips`/`voice`, включая каталог.
- `server.py:1205-1206` — `apply_answers(drop_audio=True)` вызывает это.

**Суть.** На Windows `unlink()` каталога выбрасывает `IsADirectoryError` или
`PermissionError`. Аудио не удаляется, старые каталоги клипов накапливаются;
человек получает ошибку уже после применения ответов.

**Минимальное исправление.** Проверять `is_dir()` и вызывать `shutil.rmtree`;
удалять пустые родительские каталоги; добавить тест SQLite-сборки и
`drop_audio=True`.

### M10. `cleanup_jobs` может удалить файлы живой задачи

**Где:** `data_io.py:331-351`.

**Суть.** Для `.json` статус `queued`/`running` пропускается, только если файл
моложе суток; для `.log` и `.pid` проверки состояния нет вообще. Живая, но давно
не обновлявшаяся задача может потерять статус, PID и лог; `cancel_job` и
`transcription_status` перестанут её видеть. Документация обещает «идущие задачи
не трогает».

**Минимальное исправление.** Читать PID и проверять `core.alive(pid)`; пропускать
все файлы задачи, если процесс жив; удалять только завершённые задачи.

### M11. `safe_group` допускает зарезервированные имена Windows и слишком длинные имена

**Где:** `paths.py:87-88` — заменяются только символы, не являющиеся
алфанумерическими, кроме `-` и `_`.

**Суть.** Имена `CON`, `NUL`, `COM1`, `LPT1` и т.п. зарезервированы Windows;
каталог может не создаться или вести себя как устройство. Нет ограничения длины
(лимит пути/имени) и проверки регистровых коллизий. Точки и пробелы `safe_group`
заменяет на `_`, поэтому отдельной проблемы завершающих точек/пробелов здесь нет.
Группа с таким именем ломает словарь или профиль.

**Минимальное исправление.** Запрещать зарезервированные имена (без учёта
регистра и расширения), ограничить длину (например, 64 символа), проверять
коллизии без учёта регистра.

## 6. Низко

### L1. `settings.load_config` не проверяет типы значений

**Где:** `settings.py:47-50` — `cfg.update(load_overrides())` без валидации.

**Суть.** `config.json` может содержать строку вместо числа или списка; ошибка
проявится позже в случайном месте. Часть ключей валидируется по месту, но не все.

**Минимальное исправление.** Добавить схему типов для известных ключей и
понятное сообщение о неверном значении; неизвестные ключи сохранять, но не
использовать.

### L2. `tmpfiles.sweep_stale` смотрит на mtime каталога

**Где:** `tmpfiles.py:43-59`.

**Суть.** Время изменения каталога не обновляется при записи файлов внутри.
Долгая задача с постоянным каталогом может выглядеть «старой» и быть удалена
через 12 часов, хотя работает.

**Минимальное исправление.** Проверять самый свежий файл внутри или возраст
создания плюс признак активной задачи; увеличить порог для известных долгих
задач.

### L3. `selfcheck.run_tests` не изолирует `TEMP`/`TMP`

**Где:** `selfcheck.py:57-67`.

**Суть.** Задаётся только `RUS_TRANSCRIBER_DATA`; `TEMP`/`TMP` наследуются, а
`PYTHONDONTWRITEBYTECODE` не выставляется. Тесты могут писать во временный
каталог пользователя и создавать `__pycache__` в репозитории.

**Минимальное исправление.** Создавать отдельный sandbox для `TEMP`/`TMP` и
удалять его; выставлять `PYTHONDONTWRITEBYTECODE=1`.

### L4. Выбор порта OpenCode подвержен TOCTOU

**Где:** `llm_provider.py:67-80` — порт выбирается через `bind`, сокет
закрывается, затем запускается `opencode serve` на этом порту.

**Суть.** Между закрытием сокета и стартом OpenCode порт может занять другой
локальный процесс. Клиент отправит ему basic-auth и текст. Окно маленькое, но
это локальная утечка.

**Минимальное исправление.** Проверять, что порт занял именно запущенный процесс;
при ошибке старта выбирать новый порт; по возможности передавать уже открытый
сокет.

### L5. `confirm._write` использует фиксированный временный файл

**Где:** `confirm.py:85-89` — `p.with_suffix(".tmp")`.

**Суть.** `approve`, `consume` и `reject` могут одновременно писать
`pending.tmp`/`approved.tmp`; одно разрешение может потеряться, и человеку
придётся подтверждать снова.

**Минимальное исправление.** Уникальный временный файл + `os.replace`; при
желании — блокировка на файл подтверждений.

### L6. `core.launch` пишет PID после запуска процесса

**Где:** `core.py:111-113` — `Popen`, затем `pid.write_text`.

**Суть.** Если запись PID не удалась (диск, права), процесс уже работает, но
`cancel_job` не сможет его найти. Процесс останется сиротой.

**Минимальное исправление.** Писать PID во временный файл и заменять; при ошибке
пытаться завершить только что запущенный процесс и вернуть понятную ошибку.

## 7. Проверено и не является ошибкой

### 12.3. Средне

#### M12. В сохранённом процессе сбой модельного этапа после успешного сохранения помечает задачу `error`

**Где:**
- `worker.py:1366-1379` — после `_save_worker_result` вызывается
  `_execute_workflow_model(st)`; общий `except Exception` пишет `state="error"`.
- `worker.py:1241-1257` — то же для конвейера слов.
- `worker.py:1437-1458` — `_execute_workflow_model` ловит только
  `llm_provider.ProviderError`.
- `workflow.py:511-526` — `get` и проверки состояния выбрасывают `storage.Conflict`;
  `prepare_model_task` (`workflow.py:258-261`) тоже.
- `storage.py:27-40` — `Conflict` и `Busy` — подклассы `StorageError`, но не
  `ProviderError`.

**Суть.** Стенограмма уже сохранена (JSON, MD, SQLite-commit), но `workflow.get`
или `prepare_model_task` (а также начальные проверки `execute_model`) могут
выбросить `Conflict`, `Busy`, `KeyError` или `ValueError` из-за обычной смены
состояния запроса: он отменён, уже обработан, политика изменилась или БД занята.
Исключение уходит в общий `except` и переводит задачу в `error`, хотя результат
готов. Это противоречит docstring `worker.py:1438` («ошибки не скрывают готовую
стенограмму»).

**Последствия.** Пользователь или агент видит ошибку и может повторить
распознавание; статус `done` с `model_error` не сохраняется; причина сбоя
теряется в общем trace.

**Минимальное исправление.**
1. Обернуть весь модельный этап в отдельный `try/except` и возвращать
   `{"model_state": "failed", "model_error": ...}`.
2. Ловить как минимум `storage.StorageError`, `KeyError`, `ValueError`, `OSError`;
   не менять `state="done"` после успешного сохранения.
3. Сохранять traceback в лог, но не в состояние задачи.
4. Тест: `workflow.get` выбрасывает `Conflict` после сохранения — статус `done`,
   файлы на месте, `model_error` заполнен.

#### M13. PID-файлы не удаляются, а `cancel_job` не проверяет владельца PID

**Где:**
- `core.py:111-113` — PID пишется после `Popen`; удаления нет.
- `core.py:59-63` — `pid_of` читает файл.
- `core.py:79-90` — `job_status` считает активную задачу живой, если жив процесс
  с этим PID.
- `core.py:117-139` — `cancel_job` делает `taskkill /PID ... /T /F` без проверки,
  что это процесс задачи.
- `data_io.py:331-351` — `.pid` удаляется только `cleanup_jobs` через 30 дней.
- В `worker.py` нет `.pid`/`unlink` (проверено поиском).

**Суть.** Windows переиспользует PID. Если worker был убит, питание пропало или
статус не успел обновиться, остаётся `.pid` со старым номером. Когда этот номер
получит другой процесс, `job_status` будет считать задачу живой, а `cancel_job`
завершит чужое дерево процессов. Даже без переиспользования старые `.pid`
накапливаются и мешают очистке.

**Последствия.** Возможно завершение постороннего пользовательского процесса
(тот же пользователь, но другая программа), вечное «выполняется» у мёртвой задачи,
ложные отмены.

**Минимальное исправление.**
1. Хранить рядом с PID признак владельца: время создания процесса или случайный
   токен задачи; перед `taskkill` сверять его.
2. Удалять `.pid` в `finally` worker и при переходе в `done`/`error`/`cancelled`.
3. В `job_status` при несовпадении признака считать процесс чужим, а задачу —
   завершившейся без итога.
4. Тест: `.pid` указывает на живой посторонний процесс — `cancel_job` не убивает
   его, статус становится `error`.

#### M14. Legacy-сохранение стенограммы неатомарно; читатели не берут блокировку

**Где:**
- `transcript.py:284-286` — `data["source_revision"] += 1`, затем
  `Path.write_text` для JSON, затем для MD.
- `transcript.py:196-215` — `save`/`save_new` берут `conspect.write_lock`, но
  `_save_locked` пишет напрямую.
- `transcript.py:289-300` — `load` читает JSON без блокировки.
- `recordings.py:89-93` — `open_for_document` тоже читает JSON напрямую.
- `conspect.py:77-87` — уже есть атомарный `_replace_bytes` (уникальный temp +
  `os.replace`), который здесь не используется.
- SQLite-ветка (`transcript.py:262-282`) коммитит запись и материализует
  документы иначе; проблема относится к `legacy_files` по умолчанию.

**Суть.** `Path.write_text` сначала обрезает файл, поэтому падение или заполнение
диска посреди записи оставляет обрезанный JSON. MD пишется отдельно: если JSON
записался, а MD нет, ревизия уже новая, а пара файлов рассинхронизирована.
Читатели не берут `write_lock`, поэтому даже успешная запись может быть прочитана
в промежуточном состоянии (пустой или частичный JSON). Блокировка защищает только
писателей.

**Последствия.** Потеря стенограммы при сбое, `JSONDecodeError` у читателя,
расхождение JSON и MD, повторный запуск с неверной ожидаемой ревизией.

**Минимальное исправление.**
1. Писать JSON и MD через уникальный временный файл в том же каталоге,
   `flush` + `fsync`, затем `os.replace` (как `conspect._replace_bytes`).
2. Сначала готовить оба временных файла, затем заменять; при ошибке не оставлять
   частичный файл и сообщать, какой шаг не выполнен.
3. В `transcript.load` для legacy добавить несколько повторов чтения при
   `JSONDecodeError` (как в `core.job_status`) или брать общий lock на чтение.
4. Тест: сбой записи после частичного JSON — старый файл остаётся валидным;
   параллельное чтение во время сохранения не видит невалидный JSON; сбой MD
   оставляет JSON валидным и даёт понятную ошибку.

#### M15. Пакетное применение ответов в legacy-режиме неатомарно

**Где:**
- `core.py:1513-1528` — каждый ответ: `transcript.load`, `transcript.apply_review`
  (сохраняет), отчёт.
- `core.py:1534-1544` — каждый свободный ответ: `P.apply_free` (сохраняет через
  `apply_word_edits`).
- `core.py:1573-1574` — `P.mark_applied` только после всех циклов.
- `review_pack.py:643-644` — `apply_free` вызывает `T.apply_word_edits`.
- `review_pack.py:762-783` — `mark_applied` пишет `applied_answers`.
- `core.py:1416` — общий `conspect.write_lock` сериализует процесс, но не делает
  пакет транзакцией.

**Суть.** В legacy-режиме при сбое на ответе N ответы 1..N-1 уже записаны в
стенограмму, но `applied_answers` не обновлён. Повторный вызов снова видит их как
неприменённые; для свободного текста `freeform.plan` может вставить фрагмент ещё
раз, для решений — выдать `not_found` или конфликт. Пользователь получает общую
ошибку без отчёта о частичном применении.

**Последствия.** Частично применённый пакет, повторные вставки, потерянные снимки
отмены, невозможность понять, что уже применено.

**Минимальное исправление.**
1. После каждого успешного ответа сразу вызывать `mark_applied` с его id, снимком
   и итогом; при сбое сохранять уже применённые.
2. Либо собрать все правки и сохранять одной операцией (потребует разделения
   `apply_review`/`apply_free` на «план» и «запись»).
3. Возвращать отчёт о частичном применении и id сбойного ответа.
4. Тест: два ответа, второй падает — первый помечен применённым и не повторяется;
   после перезапуска применяется только второй.

#### L8. В SQLite-режиме подтверждение ответов ломается от событий страницы

**Где:**
- `core.py:944-946` — `state_hash` считается по всему `state`.

к содержанию ответов, поэтому это ложный конфликт.

**Последствия.** Человек вынужден подтверждать заново; при активной странице
подтверждение может не проходить вовсе.

**Минимальное исправление.** Хешировать только поля, влияющие на подтверждение:
`version`, выбранные `answers` (id, kind, text, audio/word_ids) и соответствующие

`applied_answers`. Тест: добавить событие между prepare и confirm — подтверждение
проходит; изменить текст ответа — не проходит.

### 12.5. Проверено и не является ошибкой

- `restore_recording_revision` (`core.py:607-656`): `prepare_restore_snapshot`
  вызывает `recordings.operation_context`, а тот — `storage.capture_context`
  (`storage.py:932-945`). `capture_context` возвращает детерминированные данные
  из БД (без нового UUID и времени), поэтому повторный снимок при неизменном
  состоянии совпадает, и сравнение `current != snapshot` (`core.py:638-641`)
  работает как защита. Подозрение на ложный конфликт не подтвердилось; изменение
  имени пользователя или ревизий действительно инвалидирует снимок — это ожидаемо.
- `conspect.write_lock` (`conspect.py:41-63`) реентерабелен: `threading.RLock` +
  thread-local `_held_locks`; вложенные `save_new` → `ensure_new_result` и
  `apply_answers` → `apply_review` не блокируют сами себя.
- `storage._transaction` (`storage.py:828-852`) при вложенном вызове использует
  SAVEPOINT, поэтому вложенные операции не падают с «transaction within a
  transaction».
- `server._gated` (`server.py:93-109`) перехватывает `core.CoreError`,
  `storage.StorageError` (включая `Conflict`/`Busy`), `ValueError`, `KeyError`,
  `OSError`; ошибки возврата ревизии и применения ответов доходят до клиента
  текстом, а не роняют сервер.
- `jobslots.acquire` (`jobslots.py:26-51`) держит OS-lock; файл `slotN.owner` —
  только информационный, его устаревание не блокирует очередь. Отдельного дефекта
  здесь нет.

- **M13 исправлен:** PID-файл хранит метку запуска процесса (Windows `GetProcessTimes`,
  Linux `/proc/<pid>/stat`). Если PID достался другому процессу, задача считается
  потерянной и ничего не завершается; если принадлежность подтвердить нельзя (старый
  PID-файл без метки), `cancel_job` отказывает, не трогая процесс и статус.
- **L4 исправлен:** до отправки пароля и текста проверяется, что порт слушает запущенный
  OpenCode или его потомок; при чужом слушателе берётся новый порт (до трёх попыток).
- **M7 (возобновление миграции)** отложен вместе с П7 по решению владельца.
- Проверки: синтетический `unittest` в Linux-песочнице — новые тесты проходят; три
  прежних падения связаны с окружением песочницы (нет `torch`, пути Windows) и есть
  без этих правок. Окончательная проверка — CI на Windows.
