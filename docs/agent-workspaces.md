# Параллельные задачи и автоматическое обслуживание

Один GitHub-репозиторий, отдельный клон на каждом компьютере, отдельная рабочая копия
каждой одновременно изменяемой задачи. Общая папка исходников через облачный диск
не используется. Worktree не изолирует базы, окружения, порты и пользовательские данные.

## Уже работающие механизмы

- [GitHub](ci-automerge.md) проверяет PR, обновляет отставшие ветки, выполняет автослияние
  нечерновых PR и дважды в сутки убирает подходящие удалённые ветки.
- Claude сохраняет штатные `.claude/worktrees`, resume и встроенную очистку.
  Ручной checkout не равнозначен встроенной изолированной сессии.
- OpenCode V2 использует `.opencode/worktrees` по проектному конфигу.
  Создание worktree и перенос сессии — разные операции.

Общие настройки проекта не содержат личных моделей, разрешений, токенов и путей.
Локальная автоматизация ниже — opt-in: она не включается у других разработчиков
только от клонирования репозитория и не поставляется как часть MCP-сервера.

## Локальная страховка

Исходники: `tools/agent_workspaces.py` и `tools/opencode-workspaces/`.
Их проверенную копию размещают вне изменяемых feature-веток. Задание Планировщика
и hooks не должны исполнять текущий произвольный код PR.

Личный конфиг вне репозитория содержит:

```json
{
  "state": "<absolute local registry directory>",
  "opencode": "<absolute opencode executable>",
  "repos": [
    {
      "root": "<absolute canonical clone>",
      "github": "owner/repository",
      "excluded": ["<existing checkout not owned by this automation>"]
    }
  ]
}
```

Строки с `<...>` — места для локальных значений, не готовая конфигурация.
Существующие копии явно исключаются при первоначальной установке.

### OpenCode

В локальном конфиге клона подключается пакет `tools/opencode-workspaces` из доверенной
копии с options `config`, `python`, `script` — абсолютными локальными путями.
Плагин ограничен перечисленными репозиториями; прочие проекты он не обслуживает.
Перед первой build-задачей получает свежую базу, создаёт worktree и переносит сессию.
При недоступном `origin` копия создаётся от последней загруженной `origin/main`
(не от локальной ветки `main`, которая может отставать), а сессия получает
предупреждение. Штатный `worktree.create` тоже создаёт отдельную ветку
от проверенного коммита (по умолчанию свежий `origin/main`); явно заданная исходная
ссылка сохраняет свой смысл. Уже существующие detached-копии не переключаются.
Чтение/планирование в основном checkout само по себе не создаёт копию.
Новая копия не создаётся на каждое сообщение; продолжение использует location сессии.
Команда `/workspace` позволяет проверить этот путь без обращения к модели.
Инструменты записи блокируются, если перенос ещё не применён.
Внимание: это не системная песочница и не запрет абсолютных путей. Живая проверка
21.11.2026 на OpenCode 2.3.2 (установленная доверенная копия плагина из PR №69):

- запрос оболочки (`shell.create`) с рабочей папкой в основном клоне и в его вложенной
  папке отклонён сообщением плагина, тот же запрос вне клона выполнился;
- сессия build в основном клоне, получив просьбу создать файл, получила отдельную
  рабочую копию и ветку от `main`; файл записан там, основной клон остался чистым;
- живьём не проверено: чтение в основном клоне, Desktop и TUI (включая режим `!`),
  сценарий отложенного переноса, когда первый вызов инструмента отклоняется.

Проверять нужно с указанием location основного клона (`location[directory]`): запрос без
него идёт в другой location, где плагин не подключён, и ложно показывает отсутствие
защиты. Проверка относится к версии плагина из слитого PR; после каждого обновления
копии `trusted` её повторяют.

В V2.3.2 встроенная Git-стратегия создаёт detached checkout. Эта автоматизация
заменяет её для своего настроенного проекта: ветка создаётся вместе с новой копией.
Команда `/workspace-done` завершает задачу и архивирует её сессию без удаления истории.
Для результата без изменений агент завершает задачу этой командой; закрытие ответа
само по себе не служит сигналом удаления.

Shell-запуски в копии и её вложенных каталогах получают изолированные
RUS_TRANSCRIBER_DATA/TEMP/TMP и настройки Python без байткода. Это не контейнер
и не перехват любых абсолютных путей команды.

### Claude

В личные настройки добавляются SessionStart и SessionEnd hooks, вызывающие:

```text
python -B <trusted agent_workspaces.py> --config <local config> claude-hook
```

Вход hooks читается из stdin. Основной клон и другие проекты игнорируются.
SessionStart регистрирует новую разрешённую копию и владельца; SessionEnd помечает
завершение сессии, но не удаляет её содержимое. Живой Claude и native-lock запрещают
удаление даже после SessionEnd. Штатный WorktreeCreate не заменяется.

### Проверка и уборка

```text
python -B <trusted agent_workspaces.py> --config <local config> sweep --report <report file>
python -B <trusted agent_workspaces.py> --config <local config> sweep --apply --report <report file>
```

Без `--apply` удалений нет. Первый запуск и тесты выполняются именно так.
Рекомендуется настроить Планировщик на запуск уборки раз в сутки; хуки Claude и запуск
OpenCode её не запускают.
Режим `--apply` включается отдельно после проверки пробного режима.
Если сеть, GitHub, процесс или состояние сессии проверить нельзя — копия сохраняется.
Причина записывается в локальный `last-sweep.result`, без содержимого файлов.
`--report` дописывает читаемую запись: время UTC, режим, ветку и путь рабочей копии,
статус и причину каждой задачи; имена и содержимое файлов задачи не записываются.
На Windows рекомендуемый путь отчёта —
`%LOCALAPPDATA%\OpenCodeAgentWorkspaces\reports\sweep.log`. При последующем запуске
из этого файла удаляются только распознанные записи механизма старше 30 дней;
неизвестные строки сохраняются. Данные отчёта включают локальные пути и имена веток.

Для копии с собственными коммитами удаление возможно только при всех условиях:

1. Копия зарегистрирована, находится непосредственно под одним из разрешённых
   worktree-каталогов, относится к ожидаемому общему Git и не является junction/symlink.
2. Нет native-lock, активного владельца и изменений, включая ignored/untracked-файлы.
3. GitHub подтверждает merged PR с точным head этой ветки, основой main, без открытого
   PR. Merge commit присутствует в свежей origin/main; remote-ветка не ушла вперёд.
4. После сетевых проверок ветка/head/чистота проверены повторно.

Отдельный случай без PR: явно завершённая задача, которая при регистрации была точно
на origin/main и с тех пор не получила ни одного коммита или файла. Она может быть убрана
без GitHub-слияния. Копии, принятые уже с коммитами, этим исключением не пользуются.

OpenCode-сессии перед удалением копии переносятся в основной клон и архивируются,
а не удаляются. Busy и недавно использованные сессии сохраняются. Для squash локальная
ветка удаляется только после проверки точного head слитого PR. Main обновляется лишь
fast-forward при чистом основном checkout. Неизвестные/отсутствующие копии и чужие
блокировки автоматически не восстанавливаются и не удаляются.
Перед удалением своей idle-копии уборщик выгружает её runtime-location OpenCode:
иначе V2.3.2 может оставить в кэше уже несуществующий путь и отказать при reload.
После уборки удаляется только помеченный disposable sandbox этой задачи, без перехода
по ссылкам. Журнал завершённых задач хранится 30 дней; незавершённые записи по возрасту
не удаляются.

### Обзор всех копий

```text
python -B <trusted agent_workspaces.py> --config <local config> inventory --report <report file>
```

Команда только читает: ничего не удаляет и не переносит, реестр не меняет и не блокирует на время
запросов к GitHub. Для основного клона и каждой рабочей копии из `git worktree list` она показывает:
вид (основной клон, копия под разрешёнными каталогами, копия вне них), ветку и короткий хэш, число
изменений, блокировку, учтена ли копия (`registered`, `excluded` или `unregistered`), активен ли
процесс Claude, который её вёл, и состояние PR с точно таким же head (`merged`, `open`, `closed`,
`none`, `head-differs`, `unknown`; GitHub только читается через `gh`). В отличие от `sweep`, видны и
копии, которые уборщик не ведёт: в том числе вне `.claude/worktrees` и `.opencode/worktrees`.

Поле `hint` — подсказка человеку, а не решение: `ok` (основной клон на `main` и чист),
`review-removal` (копия на месте, чиста, не заблокирована, её владелец не активен, PR с её точным
head слит: человек решает, убирать ли), `check` (основной клон не на `main` или с изменениями,
каталог копии отсутствует), иначе `keep`. Если что-то проверить нельзя, копия получает `keep` или
`check`, но не `review-removal`. `--no-github` не обращается к GitHub. `--report` дописывает строку
`AgentWorkspaceInventory …` в тот же журнал, что и `sweep`, или в отдельный файл (например,
`%LOCALAPPDATA%\OpenCodeAgentWorkspaces\reports\inventory.log`); записи старше 30 дней убираются так
же, неизвестные строки сохраняются. В отчёте локальные пути и имена веток, но не имена и содержимое
файлов. Запуск из Планировщика под другой учётной записью или без прокси может не достать до
GitHub: тогда в поле `pr` будет `unknown`.

## Версия выпуска и сборка

VERSION остаётся строковым литералом в server.py и повышается при изменении server.py.
При механическом конфликте выбирается следующая версия после текущей в main.
Build ID дополняет VERSION и различает сборки с одинаковым номером, но не заменяет
повышение VERSION. Версии схем данных независимы.

`buildinfo.py` собирает полный SHA, clean/dirty/unknown и SHA-256 согласованного состава
поставки, не импортируя приложение. Установщик проверяет копию и создаёт build-info.json;
диагностика, ASR-метаданные и паспорт теста скорости читают отдельный build ID.
Без Git и пригодного манифеста происхождение неизвестно. Изменение поставленных файлов
помечается modified/dirty. Манифест не является цифровой подписью и не доказывает доверие
к произвольному архиву; личные данные, абсолютные пути и секреты в него не включаются.

Проверки уборки выполняются только на временных синтетических репозиториях. Обновление
проверенной локальной копии автоматизации — отдельное явное действие; обновление MCP-установки,
слияние черновых PR и пользовательские данные к обслуживанию worktree не относятся.
