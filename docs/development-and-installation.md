# Разработка и установленная программа — разные папки

## Правило

- **Клон для разработки** — отдельная папка с `.git` (латинский путь, вне OneDrive и вне
  папки программы), например `%USERPROFILE%\src\rus-transcriber`. Агенты-разработчики
  работают только здесь.
- **Установленная программа** — папка, куда её копирует `install.ps1` (по умолчанию
  `%LOCALAPPDATA%\rus-transcriber`), без `.git`. Её меняет только установщик; код в ней не
  правят — следующее обновление перезапишет правки.
- **Данные** — отдельная папка данных (`RUS_TRANSCRIBER_DATA`, по умолчанию
  `%APPDATA%\rus-transcriber-data`); ни клон, ни установка её не содержат.

`install.ps1` это проверяет: удаление программы отказывает, если в её папке есть `.git`,
а установка из другой папки отказывает, если в папке установки есть `.git`.

## Если программа уже стоит в папке рабочей копии Git

Раньше программу можно было ставить прямо в клон. Чтобы развести:

1. В старой папке проверить, что не потеряется: `git status`, `git branch -vv`,
   `git log --branches --not --remotes --oneline`, `git stash list`.
2. Создать новый клон из старой папки (сохранит локальные ветки):
   `git clone <старая папка> <новая папка>`, затем в новой
   `git remote set-url origin https://github.com/denII-sudo/rus-transcriber.git` и `git fetch`.
   Незакоммиченные правки перенести патчем (`git diff` → `git apply`) или коммитом.
3. Убедиться, что в новом клоне есть всё из шага 1.
4. Только после этого убрать `.git` и файлы разработки из папки программы и запустить
   `install.ps1 -Target <папка программы>` из нового клона. Данные и настройки
   приложения ИИ-агента не меняются.

## Обновление установленной программы

В клоне: `git fetch`, перейти на нужную версию (ветка `main` или проверенный тег), затем
запустить `install.ps1` из клона. Откат — та же последовательность с прежней версией;
прежние версии пакетов окружения — из снимка `cache\pip-freeze\before-update-*.txt` в папке
программы (`.venv\Scripts\python.exe -m pip install -r <снимок>`).

Установщик сам проверяет источник: коммит должен быть в `origin/main` (по последнему
`git fetch`) или под тегом, без незакоммиченных изменений. Иначе он спрашивает человека, а без
терминала отказывает, пока не указан `-AllowUnreviewedSource`. Ставить код из рабочей ветки
в установленную программу — только сознательно и по согласию владельца.

Что ставится: файлы верхнего уровня клона `*.py`, `*.html`, `*.tsv`, а также `README.md` и `install.ps1`, четыре документа из `docs/` и папки `tools`, `tests`, `examples`. Правило для корня задаёт `buildinfo.py` (`root_files`), установщик берёт список у него (`buildinfo.py --list-root`), поэтому новый модуль никуда вписывать не нужно, а служебные скрипты, которые ставить не надо, кладите в `tools/`. Скрытые файлы, имена не из латиницы, цифр и `_.-` и стенограммы (`*.transcript.*`) не ставятся; ссылка (symlink/junction) с именем файла программы — отказ до копирования. Лишние файлы в корне установленной папки установщик не удаляет, самопроверка их не учитывает.

Шаг 8 «База записей» (`rt.py db-init`, функция `recordings.prepare_new_installation`): если в папке данных нет следов работы с записями в файлах, установщик создаёт пустую `state.sqlite3` и записывает `recording_backend: sqlite` в `config.json`; иначе ничего не меняет. Существующую базу и её резервы не открывает на запись. Если выбрано хранение в базе, а базы нет, или базу создать не удалось, установка доходит до конца и завершается с кодом 2. При агентской установке это значит: прочитать строку шага 8, а не повторять установку. Посмотреть, что сделал бы шаг, не меняя ничего: `rt.py db-init --check` с `RUS_TRANSCRIBER_DATA` нужной установки.

Порядок на практике:

1. **Зафиксировать версию.** `main` между проверкой и запуском может уйти вперёд (слился чужой
   PR). Ставьте тот коммит, который человек одобрил (`git log -1` перед запуском), а если
   `main` успел измениться — сначала скажите, что ещё войдёт в установку.
2. **Основной клон должен стоять на `main`.** Если он оказался на другой ветке (её ведёт
   другой человек или агент), не переключайте его сами и скажите владельцу; для установки
   сделайте отдельную рабочую папку Git с `main` —
   `git worktree add <папка> main` (или `--detach origin/main`) — и запускайте `install.ps1`
   из неё. Установщик принимает её как клон. После обновления папку можно убрать
   (`git worktree remove <папка>`).
3. **Агент запускает установщик с явными флагами:** `-Target`, `-DataDir`, `-SkipClaudeConfig`,
   при обновлении `-KeepSavedToken`. `-AllowRunningServer` — только если записи сейчас не
   обрабатываются; после обновления человек перезапускает приложение ИИ-агента: до этого его
   сервер работает на прежнем коде.
4. **Вопросы установщика.** В терминале установщик может спросить (например, удалять ли лишние
   файлы в `tools`/`tests`/`examples`; пустой ответ — «удалить»). Без терминала вопросы не
   задаются, а этот ответ считается пустым. Запуская установщик во вкладке, которую видит
   человек, предупредите его заранее, что отвечать будет он.
5. **Проверка после обновления:** итог шага 11 (самопроверка) и версия в начале вывода; при
   сомнениях — побайтное сравнение файлов программы с выбранным коммитом.

## Переносы строк

В репозитории `.gitattributes` задаёт LF для всех текстовых файлов на любом компьютере,
независимо от `core.autocrlf`. Клон, созданный до этого правила, сохраняет прежние CRLF в
неизменённых файлах; чтобы привести его к LF, при чистом `git status` выполните
`git checkout-index --force --all`. Установщик копирует файлы как есть, поэтому после
этого следующее обновление тоже даст установку без смешанных переносов.

## Совместная разработка

Размещение рабочих копий, возобновление задач, локальная страховка после слияния и
различие VERSION/build ID описаны в [автоматическом обслуживании задач](agent-workspaces.md).

Источник истины — `denII-sudo/rus-transcriber`, ветка `main`: обязательна проверка `tests`
(Windows). PR, прошедший проверки, сливается автоматически; PR другого участника, меняющий
файлы владельца кода (`.github/CODEOWNERS`: код, установщик, CI, `AGENTS.md`), сначала ждёт
одобрения владельца — подробнее в `docs/ci-automerge.md`. Остановить слияние можно, переведя PR
в черновик. Работа — в короткой ветке от свежего
`main` (у участников — в своём fork, `upstream` — основной репозиторий) и pull request в
`main`. Общие правила агентов —
`AGENTS.md`; личные правила каждого разработчика хранятся у него, не в общих файлах.
Как PR сливаются сами после проверок и что делать, если PR застрял, — `docs/ci-automerge.md`.

Сессии Claude Code в этом проекте настроены в `.claude/settings.json`. Автосжатие срабатывает
на 45% контекста (`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`). С 35% хук `.claude/hooks/context-warning.ps1`
предупреждает и предлагает `/compact`, повторяет это один раз на 40% и дальше молчит до сжатия.
Заполнение он считает по транскрипту сессии при окне 1 млн токенов; другое окно задаётся
переменной `RT_CONTEXT_WINDOW_TOKENS`, порог — `RT_CONTEXT_WARN_PCT`. Хук ничего не блокирует
и сжатие не запускает. Перезапуск сессии не нужен: 23.11.2026 хук сработал в сессии, открытой
до появления этих файлов в рабочей копии; его сообщение видно в окне приложения Claude. Что в такой
сессии срабатывает и автосжатие на 45%, пока не проверено. Сессия в отдельной копии
(`.claude/worktrees/…`) берёт настройки из своей копии: в копии, созданной раньше, их нет, пока
её ветку не обновят от `main`.

## Что проверяет `tests`

Проверка `tests` (`.github/workflows/tests.yml`, Windows) запускает модульные тесты, самопроверку как у
установленной копии и поиск личных слов в файлах репозитория.

- Оформление текстовых файлов — `tests/test_text_hygiene.py`: UTF-8, BOM только у `.ps1` (и у них
  обязательно), переносы строк LF, относительные ссылки в `.md` ведут на файлы репозитория. В копии без
  Git (установленная программа) эта проверка пропускается.
- Личные слова (имена участников, названия групп) — `tools/check_repo.py --hide-words` со списком из
  секрета репозитория `RUS_FORBIDDEN_WORDS` (по одному слову в строке). Журнал CI публичный, поэтому в нём
  только файл и строка, без самого слова. Пока секрет не задан, а также в PR из форков шаг пропускается
  с пометкой.

Секрет задаёт и обновляет владелец на компьютере с данными, не показывая слов на экране. Команда для
Git Bash (в Windows PowerShell 5.1 конвейер между программами портит кириллицу):

```bash
PYTHONIOENCODING=utf-8 python tools/check_repo.py --list-words | gh secret set RUS_FORBIDDEN_WORDS --repo denII-sudo/rus-transcriber
```

Проверить, что список дошёл целиком: в журнале шага «Check tracked files for private words» число
«слов в списке» должно совпасть с числом строк `--list-words` на этом компьютере.
