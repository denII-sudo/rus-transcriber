# Перенос записей старого файлового формата в SQLite

`tools/import_legacy.py` переносит стенограммы старого формата (`*.transcript.json` рядом с
аудио или в папке `<имя>.rus-transcriber`) в SQLite-хранилище схемы v4. Это инструмент
отдельно согласованной миграции: сам по себе он ничего не запускает, не создаёт базу и не
переключает программу на SQLite (`recording_backend` остаётся прежним). Установщик на установке, где
уже работали с записями в файлах, базу не создаёт и режим не меняет: переход — по этому документу.

## Порядок

1. Резервная копия папки данных и комплектов результатов (стенограммы, конспекты, папки
   разбора) с контрольными суммами.
2. План переноса (`plan.json`, формат ниже) — решения владельца: какие записи и варианты
   переносить, основная версия, дата записи и её источник, кем подтверждены голоса.
3. `check` — проверка в памяти: ничего не пишет, кроме отчёта.
4. Пробный перенос на копии: отдельная папка данных (`RUS_TRANSCRIBER_DATA`), база создаётся
   штатно (`initialize_recording_store`), затем `apply` и сверка документов
   (`python -m tools.verify_document_files` из папки программы).
5. Настоящий перенос и затем, отдельным решением, переключение `recording_backend`.

Старые подтверждения говорящего (`legacy_speaker_review`, карточки разбора) делаются до переноса,
а `check` повторяется по изменившимся стенограммам. Голосовые профили после переноса обучаются по
записям в базе: ручное обновление по `recording:<id>` и автопополнение при обработке; перенесённая
запись связана со старым ключом профиля и второй раз не учитывается
(`docs/voice-biometrics-policy.md`, раздел 4).

```powershell
python tools/import_legacy.py check --plan plan.json --out отчёты-check
python tools/import_legacy.py apply --plan plan.json --data-dir <папка данных> --out отчёты-apply
python tools/import_legacy.py mark-voices --plan plan.json          # показать
python tools/import_legacy.py mark-voices --plan plan.json --apply  # записать
```

Код возврата: 0 — без ошибок (`checked` или `verified_copy`), 1 — `partial`: ошибки, конфликты
или непройденные проверки (в отчёте), 2 — неверный план, окружение или `--data-dir`.

`--out` получает комплект: `inventory.json` (исходники и их SHA-256, сверка MD), `plan.json`,
`mapping.json` (старый → новый `recording_id`, правило, старый номер ревизии), `report.json`,
`verification.json` и `report.md`; статус `checked`, `verified_copy` или `partial`, активация
всегда `not_performed`. Комплект содержит приватные пути и хранится только на этом компьютере.
`apply` требует `--out` и `--data-dir`, совпадающий с папкой данных программы, и после записи проверяет
набор: `integrity_check`/`foreign_key_check` базы, `verify_files` по каждому корню, совпадение
текста/говорящих/сомнений/правок/имён со старыми файлами, исходный снимок (ревизия 1 = старый
файл по SHA-256), чтение документов без базы и пробную резервную копию базы (`rehearsal/`),
проходящую `validate_copy`.

## Что делает перенос

- Старые файлы не меняются. Новые документы формируются в подпапке `v4` папки записи
  (`<имя>.rus-transcriber\v4\<имя>[.<вариант>].transcript.*`): имена совпали бы со старыми.
- Каждый вариант стенограммы — отдельная запись базы с тем же аудио. Старый `recording_id`
  (`uuid4().hex`, ставится штатным сохранением) сохраняется в виде UUID; если его нет, ID
  вычисляется из пути и SHA-256 исходного JSON. Повторный `apply` пропускает уже перенесённое;
  тот же ID из изменившейся стенограммы — конфликт, а не перезапись.
- Ревизии в базе начинаются с 1: первая ревизия — снимок старой версии, её прежний номер
  (`source_revision`) записан как исходная точка (`quality.migration.baseline`, `mapping.json`);
  ложных промежуточных версий не создаётся.
- Пакет карточек переносится целиком (решение владельца по В-1, 26.11.2026: «Перенос целиком»;
  находка М-1 — без состояния пакета пересборка отказывала «карточка №None», а «Применить» падало).
  Подробности — раздел «Пакет карточек» ниже.
- Старый `.transcript.md` сравнивается с рендером его JSON (переносы строк не учитываются).
  Расхождение отмечается в отчёте для человека: это может быть ручная правка или другая версия
  рендера. Старые MD не меняются.
- Идентификаторы сегментов и слов назначаются адаптером `recordings.snapshots_from_worker`;
  уже присвоенные при штатном сохранении (`transcript.save`) сохраняются. Служебные поля такого
  сохранения (`recording_id`, `source_revision` и др.) в новом формате ведёт база; их прежние
  значения записываются в `quality.migration.source.legacy_runtime`.
- Ссылки сомнений «сегмент + номера слов» переводятся в `word_ids`. Устаревшая ссылка
  (текст правили после разбора) привязывается по времени, только если место однозначно:
  слова того же говорящего внутри `[t1, t2]` идут подряд и только в одном сегменте, а текст
  сомнения не встречается в нём несколько раз. Если текст места изменился, у сомнения
  пометка `migration.text_same=false`. Иначе ссылка снимается, сомнение остаётся по времени
  с пометкой `migration.anchor="not_found"` — решает человек. Статус сомнения не меняется.
- Ответы текущего пакета переносятся к существующим сомнениям с происхождением
  `origin: legacy_review_pack:<папка>`. Время ответа (`ts`) в старом формате — секунды с 1970 года;
  оно переводится в вид, который пишет и посимвольно сравнивает программа (`review_pack._now`):
  UTC `ГГГГ-ММ-ДДTЧЧ:ММ:СС`, доли секунды отбрасываются, это отмечается в отчёте пакета.
  Автор ответа в старом формате не записан и не придумывается.
- Правки и их авторы (`edits[].by`: человек или модель) сохраняются как есть.
- Метаданные (`title`, `recorded_at`, `recorded_timezone`, `container`, `codec`,
  `audio_sha256`, `audio_available`) заполняются только если их нет в стенограмме: факты — по
  файлу аудио, остальное — из плана. Источник каждого значения (например, «имя файла
  (предположение)») записывается в `quality.migration.field_sources`.
- Конспекты пересобираются из исходного текста с цитатами и связываются со словами только
  по точному тексту (`conspect.save_linked`). Составные, изменённые или неоднозначные цитаты
  остаются несвязанными и перечисляются в отчёте; их связывает человек
  (`conspect_candidates`, `conspect_link_selected`).
- Действие записывается как `system`: автора-человека нет, инициатор — владелец установки.
- `mark-voices` добавляет к фрагментам профиля пометку `confirmation` (`by`: `human` или
  `program`, примечание, чьё решение); отпечатки и `confirmed` не меняются. Перед записью
  профиль копируется в `voice-backups`. Переобучение профиля может пересоздать фрагменты без
  этой пометки.

## Пакет карточек

Источник — первая папка `review_packs` варианта: `answers.json` и `manifest.json` (текущий пакет);
архивы прежних версий карточек (`answers.<версия>.json`, `manifest.<версия>.json`) и другие папки
читаются после него. Читаются только эти JSON; клипы и `voice\` не читаются и не копируются.
Состояние ложится в снимок разбора так, как его читает `recordings.read_review_pack_state`:

- текущий пакет переносится целиком, если оба файла есть и их `version` совпадает: `question_version`,
  `questions` (карточки manifest к существующим местам; ссылки на слова — только существующие),
  `answers` (версия ответа остаётся `version`), `conflicts`, `rejected`, `undo.review_pack`
  (`manifest`, `applied_answers`, `applied_at`, `application_events`, `outcome_details`, `heard`),
  `applications`, события карточек — списком `interaction_events` (не больше 2000);
- в manifest `recording_id` — ID записи в базе, `job_json` — документ `v4`, прежние значения — в
  `legacy_*`; `source_revision` пакета и карточек — `1`, если пакет собран по той же ревизии старой
  стенограммы, что перенесена, иначе `0`: такой ревизии в базе нет, и ждущий ответ получает отказ, а
  не применяется к изменившемуся тексту;
- старая отметка «применён» без подписи (`true`) становится подписью ответа, если ответ не позже
  `applied_at`; пакет без `applied_answers` — подписи всех ответов не позже `applied_at` (прежнее правило
  `review_pack._applied_map`); `applied_at` и время в журнале применения — в ту же строку UTC, что `ts`;
- снимки отмены не переносятся (решение Архитектора Р-1, 26.11.2026): отпечаток состояния после
  переноса им не совпадёт; у таких ответов «Отменить нельзя», число — в отчёте;
- ответы и вопросы архивов, ответы другой версии и пакет, который нельзя перенести целиком (нет
  manifest или версии не совпадают), — в `undo.legacy_review_packs.files` как есть (решение
  Архитектора Р-2): программа это поле не читает, пересборку оно не блокирует;
- клипы не копируются (решение Архитектора Р-3): у старых карточек на странице нет звука, новая
  порция режет свои;
- сохранённый ответ закрытого места без отметки «применён» (состояние `saved`, кроме «пропустить» и
  «повторить») получает событие переноса «место уже решено» (`action: legacy_import`, `outcome:
  already_decided`) и не применяется (решение владельца Р-4, 26.11.2026); число — `already_decided_marked`
  в отчёте. Такой ответ больше не ждёт «Применить» и не мешает пересборке. Защита «Применить»
  (`core._apply_answers_files_once`) пропускает только это событие переноса, а `review_pack.decisions` и
  `review_pack.free_answers` такой ответ не применяют — ни кнопку, ни «свой текст». Прочие ответы без
  автора-человека, в том числе ответы открытых мест, ждут человека. Ответ поверх применённого (неприменённая
  отмена, новый ответ) не помечается: его состояние от пометки не зависит;
- «Применить» отказывает всей записи, пока в пакете есть неприменённый ответ без автора-человека.
  Выходы штатные: подтвердить ответ (`request_review_answer_verification`) или ответить на карточку
  заново. Пересборка (`rebuild=true`) выходом не служит: при хранении в базе она отказывает, пока есть
  ждущие ответы.

Опись формата пакета — `LEGACY_PACK_INVENTORY` в `tools/import_legacy.py`: каждый ключ `answers.json`
и `manifest.json` (и вид файла в папке пакета) с назначением в базе или причиной, почему не переносится.
Ключ, которого в описи нет, — отказ записи `unknown_pack_keys` до записи (код 1, ключи названы в
отчёте); сухой прогон показывает его до `--apply`. Новый ключ формата пакета — сначала назначение в
описи, иначе перенос его не пропустит (закреплено тестом-описью `tests/test_import_legacy_behavior.py`).

Сведения — в `quality.migration.pack_state` и отчёте `apply`.

### Ремонт записей, перенесённых без пакета: `repair-packs`

Записи, перенесённые прежней версией (ответы с `legacy_version`, без `question_version` и
`undo.review_pack`), чинит отдельная команда. По умолчанию сухой прогон — ничего не пишет:

```powershell
python tools/import_legacy.py repair-packs --db-only --out отчёты-repair            # только по базе, без плана
python tools/import_legacy.py repair-packs --plan plan.json --out отчёты-repair     # сверка с файлами пакета
python tools/import_legacy.py repair-packs --plan plan.json --apply --data-dir <папка данных> --out отчёты-repair
```

- `--db-only` открывает только базу (на чтение) и не читает файлы рядом с аудио: какие записи
  годны по базе (`candidate`), уже исправлены, менялись после переноса или чинить нечего.
- С планом запись находится по SHA-256 старой стенограммы. Пишется, только если запись не менялась
  после переноса (ревизии стенограммы и разбора первые, от операции импорта) и ответы и вопросы в
  файлах пакета совпадают с тем, что записал перенос. Иначе — отказ с причиной (`changed_after_import`,
  `pack_files_changed`), код 1.
- `--apply` требует `--data-dir`, равный папке данных программы. Перед первой записью — резерв базы
  `db-backups\state-before-pack-repair-<UTC>.sqlite3` с проверкой `validate_copy`; не удался — ничего
  не пишется, код 2. Повреждённая копия правки, как у других штатных резервов, — не отказ, а список
  `backup_damaged_copies` в отчёте. Затем на запись — одна новая ревизия разбора (стенограмма не
  меняется) и документы `v4` штатно (`guard_before_write` отказывает при внешней правке). Ответы
  закрытых мест помечаются «место уже решено», как при переносе (сухой прогон показывает число).
- Сбой записи документов после записи в базу — статус `repaired_documents_pending` (код 1): база уже
  исправлена, документы `v4` — нет. Повтор `--apply` дописывает только документы (`documents_written`);
  внешняя правка документа — `documents_conflict` (отказ). Повтор после полного ремонта и запись,
  перенесённая новым переносом вместе с пакетом (в том числе только с архивом), — `already_repaired`.
- Ключ пакета вне описи — `unknown_pack_keys` (отказ до резерва и записи), как при переносе.
- Старые файлы, клипы и аудио ремонт не меняет и не удаляет.
- Запуск на рабочей базе и на каждой другой установке — отдельное согласие владельца; сначала —
  на копии.
- Простая копия файла `state.sqlite3` — не песочница: она активна, её корни документов указывают на
  настоящие папки рядом с аудио, и `--apply` на ней перепишет настоящие документы `v4` (рабочая база
  потом увидит их как правку снаружи). `--data-dir` этого не ловит: он сверяет только папку данных.
  Копию для пробы разворачивать только восстановлением из резерва с переназначением всех корней в
  песочницу (`rt.py db-restore … --root ID=ПУТЬ` или `core.restore_from_backup` в процессе песочницы)
  и до `--apply` убедиться, что все корни указывают в песочницу.

### Старые номера задач после переключения на `sqlite`

После переключения на `sqlite` старый номер задачи ведёт к перенесённой записи. Подходит единственная запись базы, перенесённая из этого файла и с тем же содержимым (SHA-256); статус задачи тогда показывает `recording_id`, `legacy_json` и `redirected_from`. Если такой записи нет — запись не перенесена, файл изменён после переноса, файла нет или копий несколько, — отказ называет причину и найденные `recording:<id>`. Если старого файла нет и по его пути в базе ничего нет (например, стенограмму переносили из другой папки), отказ просит найти запись в списке записей и указать `recording:<id>`: по имени файла запись не угадывается. Прямой путь к старой стенограмме не переадресуется: отказ подсказывает `recording:<id>`.

## Формат плана

```json
{
 "version": 1,
 "recordings": [{
   "audio": "C:\\...\\встреча.mp3",
   "metadata": {"title": "встреча", "recorded_at": "2026-11-06T20:32:00+07:00", "recorded_timezone": "+07:00"},
   "field_sources": {"title": "имя файла (предположение)", "recorded_at": "указание владельца"},
   "variants": [{"transcript": "C:\\...\\встреча.rus-transcriber\\встреча.v2.transcript.json",
                 "tag": "v2", "order": 2, "main": true,
                 "main_note": "основная версия вычислена по истории обработки",
                 "history": "кратко: когда и чем обработано",
                 "conspects": ["C:\\...\\встреча.v2.конспект.conspect.json"],
                 "review_packs": ["C:\\...\\встреча.v2.review"]}]
 }],
 "voice_confirmation": {"<группа>": {"by": "human", "note": "...", "decided": "..."}}
}
```

У каждой записи ровно одна основная версия; одна стенограмма не может входить в план дважды.

## Ограничения

- Проверено на синтетике (`tests/test_import_legacy.py`, `tests/test_import_legacy_packs.py`) и на
  установке владельца (до переноса пакета целиком): `check`,
  пробный перенос на копии и перенос на настоящих данных (`verified_copy`, независимая сверка) —
  `docs/2026-11-21-p7-migration-handoff.md`. На другой установке пробный перенос на копии
  по-прежнему обязателен.
- Конспект привязывается к варианту, указанному в плане; несколько конспектов с одним
  именем у одного варианта не поддерживаются.
- Старые подтверждения говорящего (`by: human` у слов без `provenance.speaker`) перенос не
  превращает в пословные подтверждения: текущие правила отбора голосов их не засчитывают.
