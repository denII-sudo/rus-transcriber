## РАР-0. Общие договорённости параллельных работ

Две доработки могут идти одновременно в разных рабочих копиях, если соблюдается следующее.

1. **Стык — только время.** Работы не вызывают код друг друга. Одна умеет вернуть отрезок
   времени своей единицы (раздел свёртки), другая — отрезки с началом и концом (горячие
   места). Соединяет их отдельный этап после слияния обеих.
2. **Чужие файлы не трогать.** Для каждой работы заранее перечислены файлы, которые она
   меняет, и файлы, которые ей запрещены.
3. **Общие файлы** (`server.py`, `README.md`, `rt.py`, `core.py`) каждая работа правит только
   в своей части. `VERSION` в `server.py` повышает каждая работа, которая меняет `server.py`;
   при конфликте ставится следующая версия после той, что в `main`
   ([AGENTS.md](../AGENTS.md), раздел «Проверки и безопасность выполнения»).
4. **Приёмка до отправки.** Ветка не отправляется, пока результат не проверен против плана:
   изменённые файлы, полный набор тестов, проверка на личные слова, пробное слияние с `main`.
5. **По умолчанию запрещено:** облачные вызовы, реальные записи, установка пакетов, скачивание
   моделей, обновление установленной программы.
6. **Каждой работе — своя рабочая копия и ветка;** основной клон остаётся на `main`
   ([agent-workspaces.md](agent-workspaces.md)). Что агент отправляет сам, а что только по
   слову человека, определяют `AGENTS.md` и личные правила того, на кого он работает.

## РАР-1. Свёртка с говорящими

**Зачем.** Автономный исполнитель получал только слова: свёртку вида «кто что сказал» этим
путём получить было нельзя, а блоки по 500 слов рвали реплики
([сверка с целью](research/product-goal-gap-2026-11.md), раздел 1).

**Что входит.**

- Задание версии 2: у слова номер реплики, у задания список реплик с условной меткой
  говорящего («Участник 1», «Участник 2»…). Задания прежнего вида доигрываются по прежним
  правилам.
- Блок не длиннее 500 слов и кончается на границе реплики; реплика длиннее предела делится по
  концу предложения.
- В облако дополнительно уходят деление на реплики и условные метки. Имена, время, аудио,
  пути и биометрия не передаются. Метки расшифровываются именами только локально, в шапке
  файла; шапка строится при каждой сборке по текущей стенограмме.
- Время начала раздела в файле свёртки — вычисляется локально по ссылкам на слова.

**Что не входит:** связь между блоками, записи длиннее 10 000 слов, короткие номера слов
вместо длинных идентификаторов, вид документа (свёртка, сводка, переработка).

**Не проверено:** качество свёртки. Его покажет только прогон на настоящей записи через
облачную модель, который согласуется отдельно.

## РАР-2. Горячие места разговора

**Зачем.** Читателю свёртки нужна навигация: где разговор был оживлён или напряжён и стоит
развернуть стенограмму или послушать запись. Предмет — место разговора, а не эмоции людей
([product-goal-and-documents.md](product-goal-and-documents.md), раздел 6).

**Что входит.**

- При обработке сохраняется слой признаков: интервалы наложений, реплики разделения голосов
  с номером кластера, громкость и высота голоса по окнам. Только числа по времени, без
  текста, имён и отпечатков голоса.
- Оценка считается при чтении по текущим словам стенограммы: отклонение громкости и высоты
  от обычных для того же говорящего в этой записи, частота смен говорящих, доля наложений.
- Показ только по запросу. В открытые документы и модельные задания слой не попадает.

**Что не входит:** модель эмоций по окнам, детектор смеха, пересчёт старых записей.

**Не проверено:** осмысленность оценок на настоящей речи. Пороги — стартовые значения без
эталона; ограничения — в [development-boundaries.md](development-boundaries.md).

## РАР-3. Стык: горячие места в свёртке

**Зачем.** Читатель свёртки должен видеть, какие её разделы стоит развернуть до стенограммы
или послушать. Обе половины готовы: раздел свёртки умеет вернуть свой отрезок времени
(`workflow.section_time_spans`), горячие места — свои отрезки (`hotspots.find_hotspots`).

**Что учтено в плане.**

- Раздел свёртки ссылается на все слова своего блока, поэтому его отрезок времени — это
  несколько минут. Пометка «раздел пересекается с горячим местом» при таком размере почти
  ничего не говорит. Поэтому пометка несёт время самого горячего места и его признаки:
  «с 00:14:10 по 00:14:40 — говорят одновременно, громче обычного».
- Пороги горячих мест не проверены на настоящей речи. Если помечено большинство разделов,
  пометка бесполезна. Поэтому показывается не всё, что выше порога, а несколько самых
  сильных мест записи (правило то же, что в РАР-5: порядок вместо порога).
- Пометки считаются при каждой сборке и каждом запросе по текущей стенограмме и нигде не
  хранятся: правка «кто говорил» сразу меняет результат, как и у самих горячих мест.
- У записей, обработанных до РАР-2, слоя признаков нет: пометок нет, причина сообщается.

**Этапы.**

| Этап | Что | Зависит от |
|---|---|---|
| 3.0 | Проба на собственных записях, только чтение и только числа: сколько горячих мест на час, какая доля разделов была бы помечена при пороге и при отборе самых сильных | запись, обработанная после РАР-2, и свёртка по ней |
| 3.1 | Чистая функция сопоставления: отрезки разделов и горячие места → пометки по разделам; не вызывает ни свёртку, ни распознавание | — |
| 3.2 | Показ по запросу: команда `rt.py hotspots` и инструмент `conversation_hotspots` выдают горячие места по разделам свёртки; локальный экран показывает пометку у раздела | 3.1; исправление показа разделов на экране |
| 3.3 | Строка пометки в файле свёртки, по настройке, по умолчанию выключено | 3.0 показала, что пометок немного и они осмысленны |

**Что не входит:** передача пометок облачной модели (отдельное решение с правкой текста
согласия), подбор порогов по эталону, пересчёт старых записей.

**Проба 3.0 (22.11.2026).** Числа и ограничения —
[research/rar-3-0-hotspots-probe-2026-11.md](research/rar-3-0-hotspots-probe-2026-11.md).
Слой признаков есть только у трёх обработок одного отрывка длиной 3,5 минуты, свёртка — у
одной и написана вручную. На этом материале: около 74 горячих мест на час, помечено 3–4
раздела из 5; на часовой записи с разделами по 4 минуты порог 0,5 пометил бы почти все
разделы. Что из этого следует:

- показывать надо несколько самых сильных мест на запись (3–5), а не всё выше порога;
- этап 3.1 от пробы не зависит, его можно делать;
- для решений по этапам 3.2 и 3.3 нужна запись длиной 30–60 минут, обработанная после
  РАР-2, со свёрткой исполнителя; до неё строку пометки в файле не включать.

**Решения владельца:** обработать ли для этого длинную запись нынешней версией и заказать
по ней свёртку исполнителя (облачный вызов, отдельное согласие); после этого — сколько мест
показывать на запись
и включать ли строку в файле.

## РАР-4. Модели распознавания и лаборатория опытов

**Зачем.** Сейчас распознают три модели: основная, вторая и третья, с голосованием «два из
трёх». Нужно знать, что даёт каждая: добавляет ли точности и насколько, либо расходует время
машины и, главное, время человека на правки и подтверждения. Вопросы направления: выбор
основной модели, перебор второй и третьей, польза четвёртой.

**Для кого.** Третий тип пользователя — тот, кто развивает программу. Лаборатория должна
переноситься на другие компьютеры и к другим людям, поэтому она не зависит от ИИ-агента и от
файлов, которые есть только на одной машине.

### Что измеряется

| Чьё время | Показатель | Нужен эталон |
|---|---|---|
| Человека | мест для разбора на час записи; доля мест, принятых без правки; время на место | нет |
| Человека | ошибки, оставшиеся без пометки | да |
| Машины | время каждого прохода на час записи | нет |
| Точность | ошибки в словах после голосования | да |

Короткие эталоны (3–5 минут, [bench-database-spec.md](bench-database-spec.md), раздел 4.3)
различают только грубую разницу. Поэтому решающими будут показатели без эталона на
собственных записях: там выборка больше.

### Гипотезы для проверки

- Вторая модель того же семейства, что основная, ошибается похоже. Замена её независимой
  моделью может дать больше, чем добавление четвёртой.
- Четвёртая модель, которая слабее основной, может увеличить число спорных мест.
- Подсветка сомнительных мест не обязательно экономит время человека: его нужно измерять.

### Что где хранится

| Что | Где |
|---|---|
| Код лаборатории, правила пригодности сборок, описания опытов, список открытых тестовых записей | этот репозиторий, папка `lab/` (слита 22.11.2026, PR №80; установщик её не ставит) |
| Известные несовместимости по классам железа, без личных данных | `docs/` этого репозитория |
| Обезличенные выгрузки прогонов по машинам, сводки по собственным записям | приватный служебный репозиторий |
| Звук, тексты, эталоны, гипотезы моделей, база прогонов | только папка данных на компьютере |

Выгрузка наружу — только явной командой человека. Правила приватности базы прогонов —
[bench-database-spec.md](bench-database-spec.md), раздел 10.

### Изменения архитектуры

1. **Граница этапов.** Пословная обработка делится на «проход модели → гипотеза» и «сведение
   гипотез → слова и пометки». Основная программа — одна фиксированная сборка этих функций,
   опыт — любая другая; так опыт измеряет то же, что делает программа.
2. **Сведение на любое число моделей.** При трёх моделях результат обязан совпадать
   с нынешним; это закрепляется тестом.
3. **Сохранение гипотез по настройке.** По умолчанию выключено. Тогда обычная обработка сама
   пополняет материал для опытов, и новое сочетание моделей не требует полной повторной
   обработки.
4. **Лаборатория вне основной программы.** Отдельная папка, которую установщик не ставит.
   Записи читает только на чтение, пишет в свою папку и в базу прогонов. Запускается
   обычными командами Python.
5. **Опыт задаётся файлом настроек:** набор моделей по ролям и правило сведения. Результат
   привязан к контрольной сумме этого файла.

Умолчания в `settings.py` ради одной машины не меняются: итог опыта — запись в `config.json`
этой машины и решение в базе прогонов.

**Этап 4.1, пригодность сборок.** Сборка — модель, среда исполнения, устройство и точность
вычислений. До любых сравнений пользы каждая сборка проверяется на общем наборе против
эталонной (процессор, fp32). Признаки непригодности: подмена устройства, ошибки и пустые
куски, превышение времени, расхождение текста с эталонной сборкой, резко иное число слов.
Непригодные сборки в опыты не попадают. Без этого вывод о модели смешивается с выводом
о сборке: например, ускоритель может считать модель неверно, не сообщая об ошибке.

**Этап 4.4, порядок опытов:** третья модель (другой движок, другая модель, без третьей);
замена второй модели независимой; четвёртая модель для мест, где не права ни одна из трёх;
основная модель. Основной может быть только модель с пунктуацией и временем слов.

**Состояние на 21.11.2026 и ближайший шаг.** Тест скорости уже отсеивает сбойные сборки:
записывает фактическое устройство, откаты, пустые и потерянные куски и не выбирает такой
вариант ([bench-measurement-status.md](bench-measurement-status.md), раздел «Пригодность
варианта»). Это закрывает большую часть этапа 4.1. Не закрыто: тест режет звук и вызывает
модель иначе, чем расшифровка, поэтому сбой времён слов он не увидит, а его голосование не
равно голосованию расшифровки. Оба пробела закрывает этап 4.2: его шаг 1 выполнен
(PR №70), тест скорости переводится на общие функции шагом 4.

**Этап 4.2 по шагам.** Каждый шаг — отдельная правка с тестом «результат прежний».

1. **Выполнен 21.11.2026 (PR №70).** Выделить в `words.py` и `worker.py` две функции
   с явным стыком: «проход модели по
   кускам → гипотеза» (слова со временем и уверенностью, сведения о сбоях) и «сведение
   гипотез → слова и пометки». Поведение не меняется; закрепляется тестом на синтетических
   гипотезах: результат при трёх моделях совпадает с нынешним.
2. **Выполнен 23.11.2026.** Сведение принимает любое число гипотез (две, три, четыре). Правило при трёх — прежнее, это закрепляют отпечатки `tests/test_combine_n_models.py`, снятые на прежнем коде. Правило для четырёх и более моделей программа не выбирает: `words.combine_hypotheses` без явного параметра `rule` (`keep` — сколько моделей должны поддержать слово основной, `replace` — сколько других должны совпасть для замены) их не сводит. До показа человеку сведение различает три состояния куска любой дополнительной модели — ошибку (`error`), пустоту по неизвестной причине (`empty_unknown`) и текст, удалённый очисткой (`filtered`); при трёх моделях результат прежний. Ключ `whisper` в `combine_hypotheses` исторический и не переименовывается: он обозначает роль третьей модели, которая может быть любого движка (PR №84). Подключение четвёртой модели к проходам и к описанию опыта в `lab/` — отдельный шаг по решению владельца.
3. Настройка сохранения гипотез, по умолчанию выключена. Гипотезы содержат текст записи,
   поэтому лежат только в папке данных рядом с записью, не попадают в выгрузки и резервные
   копии для передачи и удаляются вместе с записью. Формат получает номер версии.
4. Тест скорости вызывает те же две функции, что и расшифровка; методика получает новый
   номер версии, числа с прежними не сравниваются.

Этап не требует скачивания моделей, облака и реальных записей: проверяется на
синтетических данных. Меняются `words.py`, `worker.py`, `bench.py`, `settings.py`,
`config.example.json` и тесты; `VERSION` обновляется.

**После 4.2.** Этап 4.3 (лаборатория) ждёт базу прогонов, этапы 2–4. Первый опыт этапа 4.4
можно провести раньше, без базы и без скачивания: пересвести сохранённые гипотезы без
третьей модели и сравнить число мест для разбора и решения человека. Он отвечает на самый
дорогой вопрос — нужен ли третий проход, который занимает больше трети времени обработки.
Опыты с новой второй или четвёртой моделью требуют скачивания и согласуются отдельно.

**Решения владельца:** запуск шагов 2–4 этапа 4.2; включить ли на своей установке
сохранение гипотез после него (место на диске: текст трёх проходов на каждую запись);
сливать ли код лаборатории в `main`; нужна ли оценка разброса до следующих опытов.

### Что показал первый опыт лаборатории (22.11.2026)

Лаборатория обработала 10 записей одной установки (2,2 часа звука) шестью наборами моделей:
60 пар, без сбоев. Повторов не было, поэтому полоса разброса не измерена; точность по
эталону не измерялась — только число мест для человека и время машины. Числа относятся
к одной машине и одному набору записей.

| Набор | Мест для разбора на час звука | Время машины на час звука |
|---|---|---|
| нынешний: основная, вторая, третья — Whisper | 650 | 2379 с |
| третья — GigaAM Multilingual large | 664 | 1677 с |
| без третьей модели | 818 | 1234 с |
| вторая — GigaAM Multilingual, третья — Whisper | 695 | 2568 с |
| вторая — GigaAM Multilingual, без третьей | 848 | 1444 с |
| Whisper только на спорных кусках | 650 | 2265 с |

- **Третий проход нужен:** без него мест больше на всех десяти записях, примерно на
  четверть. Предположение «третью модель можно убрать» не подтвердилось.
- **Третьей моделью может быть GigaAM Multilingual large:** число мест то же в пределах
  неизмеренного разброса, время машины меньше на 30 %. На этом основании владелец

- **Замена второй модели на Multilingual в этом опыте пользы не дала:** спорных мест

- **Whisper только на спорных кусках** даёт те же места и экономит 5 % времени.
- Расчёт сделан до исправления PR №76: тогда один пустой кусок третьей модели отключал

- Из 102 сопоставленных решений человека в 30 правильного текста не дала ни одна модель:
  набор моделей эти места не уберёт (ср. этап 4.0 и вывод РАР-5 о местах, связанных
  с голосом).

Что не сделано: повторы для оценки разброса; пересчёт на коде после №76; четвёртая модель;
проверка на другой машине. Обезличенные итоги — в приватном служебном репозитории.

### Разброс между прогонами (сверка 21.11.2026)

При проверке шага 1 этапа 4.2 одна запись длиной 10 минут обработана четыре раза на одной
машине: по два прогона прежним и перестроенным кодом, все три прохода на процессоре,
третья модель — Whisper через faster-whisper (int8), голосовые профили отключены.

| Прогон | Согласны все три | Основной и один из двух | Спор трёх | Мест для разбора |
|---|---|---|---|---|
| прежний код, первый | 1113 | 119 | 23 | 53 |
| прежний код, второй | 1113 | 119 | 23 | 53 |
| перестроенный код, первый | 1116 | 115 | 24 | 55 |
| перестроенный код, второй | 1113 | 119 | 23 | 53 |

- Три прогона совпали полностью: слова, говорящие, голосование, места для разбора,
  диагностика проходов. Итоговый текст одинаков во всех четырёх (1259 слов).
- В одном прогоне третья модель дала другой ответ в 9 кусках из 28, на одно-два слова
  в куске. Первый и второй проходы при этом совпали, вход третьей модели тот же, код её
  вызова в обеих версиях одинаков.
- Причина не установлена. Загрузка машины между прогонами различалась: третий проход
  занимал от 239 до 687 секунд.

Что из этого следует для направления:

- **Третий проход не полностью воспроизводим.** Различие в два места для разбора на
  10 минут записи может быть разбросом, а не свойством сборки. До опытов этапа 4.4 нужна
  оценка разброса: несколько повторов одной сборки на одной записи; различия между
  сборками в пределах разброса выводом не считаются.
- **Сверка перестройки кода одним прогоном недостаточна:** нужен повтор каждой стороны.
- **Сохранение гипотез (шаг 3 этапа 4.2) снимает часть вопроса:** пересведение сохранённых
  гипотез воспроизводимо, а разброс остаётся только в самих проходах.
- Четырёх прогонов мало, чтобы судить, как часто бывает отклонение и зависит ли оно от
  загрузки машины, числа потоков или движка.

### Что показал этап 4.0

Числа относятся к собственным записям и лежат в приватном служебном репозитории. Выводы,
которые меняют порядок работ:

- узкое место — время человека: большая часть мест для разбора остаётся нерешённой;
- спор моделей даёт меньшую часть мест; больше — пометки низкой уверенности слова и близких
  голосов, которые перебор моделей не уменьшит;
- третья модель — самый долгий этап обработки;
- примерно в половине спорных мест, решённых человеком, не была права ни одна модель;
  выборка мала, это повод для опыта, а не вывод;
- все прежние записи сделаны одной сборкой и без диагностики сбоев, поэтому вывод о пользе
  третьей модели по ним ненадёжен — отсюда этап 4.1.

## РАР-5. Усилия человека на разборе сомнительных мест

**Зачем.** По этапу 4.0 программа предлагает на час записи сотни мест для разбора, человек
решает малую часть, остальное остаётся открытым. Вопрос направления — не «какой порог
поставить», а «на что человеку потратить имеющиеся минуты, чтобы итоговый конспект был
верным».

### Что человеку важно

Конечный продукт — конспект, а не дословная стенограмма. Ошибка в слове важна настолько,
насколько она меняет конспект:

- **сильно:** имена и названия, числа и даты, термины, отрицания, кто принял решение и кому
  поручено, слова внутри цитат;
- **слабо:** служебные слова, окончания, слова-паразиты, повторы, наречия;
- **«кто говорил»** важно там, где реплика попадает в конспект как решение, поручение,
  цитата или число, и почти не важно для коротких поддакиваний.

Отдельное обстоятельство программы: свёртка не может содержать цитаты, пока в записи
остаются нерешённые места. Значит, места внутри будущих цитат закрывать нужно в первую
очередь.

### Что известно из открытых источников

Обзор сделан 21.11.2026 по открытым публикациям. Прямых работ про отбор мест проверки ради
конспекта совещания не найдено: выводы — перенос из соседних задач, почти все на английском
материале. Источники прочитаны по тексту страницы или аннотации, не по полному тексту.

- Подсветка слов с низкой уверенностью по порогу сама по себе правку не улучшает: в опыте на
  36 людях качество правки с подсветкой и без неё не различалось, а при пороге, красящем
  13–21 % слов, часть людей переставала её замечать. Уверенность слова разделяет верные
  и неверные слова слабо (Kuhn и др., CHI EA 2025, <https://arxiv.org/abs/2503.15124>).
- Работает другая постановка: порядок вместо порога. Места упорядочиваются по отношению
  «ожидаемая польза к ожидаемому времени человека», берутся сверху в пределах отведённого
  времени, а оценка времени уточняется по настоящим ответам (Sperber и др., 2017,
  <https://arxiv.org/abs/1709.05227>).
- Для задач понимания текста исправление имён и содержательных слов даёт большую часть
  пользы, исправление глаголов и наречий — почти никакой (ENDow, 2025,
  <https://arxiv.org/abs/2502.13645>). Качество резюме совещаний зависит от доли ошибок
  в словах слабо (обзор CHiME-7/8, 2025, <https://arxiv.org/abs/2507.18161>).
- Калибровка делает уверенность честнее как число, но порядок мест почти не улучшает
  (<https://arxiv.org/abs/2509.07195>); усложнение оценки уверенности мало добавляет
  к простой (<https://arxiv.org/abs/1903.02852>).
- Избыток предупреждений приучает их пропускать: в медицинских системах отклоняется около
  трёх четвертей предупреждений (<https://pmc.ncbi.nlm.nih.gov/articles/PMC7646870>).
- В проверке больших наборов документов принят порядок «упорядочить, смотреть сверху,
  остановиться по правилу и оценить остаток по случайной выборке»
  (<https://arxiv.org/abs/2106.09871>).
- Языковая модель полезна как оценщик «меняет ли расхождение смысл», но как
  самостоятельный исправитель правит и верное (<https://arxiv.org/abs/2505.24347>).

Не найдено: измерений вреда именно от ошибок в числах, отрицаниях и поручениях; модели
времени на одно место; данных для русских совещаний.

### Стратегии и выбор

| Стратегия | Что даёт | Чем плоха | Решение |
|---|---|---|---|
| Поднять пороги, чтобы мест стало меньше | просто | теряются ошибки неизвестной важности; порог один на все записи | не делать первым шагом |
| Порядок по пользе и времени, показ в пределах отведённых минут | усилия идут в важное; ничего не теряется: остальное остаётся помеченным | нужна оценка важности и времени | основа направления |
| Объединение повторов: одно решение на все вхождения слова или термина | меньше карточек и набора текста | риск бездумного «да» на всю группу | второй шаг, с показом вхождений |
| От конспекта назад: сначала места, на которые опирается свёртка | проверяется то, что увидит читатель | важное вне свёртки остаётся; нужна свёртка до разбора | после порядка |
| Правило остановки и выборочная проверка остатка | честный ответ на «когда хватит» | на малых числах оценка грубая | вместе с порядком |
| Порядок, обученный на ответах этого человека | подстройка под записи и машину | нужно много ответов; риск закрепить привычку | позже, по накопленным ответам |
| Оценка важности облачной моделью | отсеивает безвредные расхождения | передача текста наружу; не проверено на русском | отдельное решение |

**Как определяется «главное».** Важность места — сумма простых признаков, которые считаются
на компьютере без облака: в месте есть число или дата; имя участника, слово из словаря
терминов или слово с заглавной буквы не в начале предложения; отрицание; варианты моделей
различаются корнем слова, а не окончанием; место внутри длинной реплики, а не поддакивания;
спор о говорящем меняет автора целой реплики; место попадает в раздел свёртки или в цитату.

**Как определяется «эффективное».** Ожидаемое время на место зависит от его вида: выбрать
один из двух вариантов — быстро; послушать, чтобы решить, кто говорил, — дольше; набрать
свой текст, когда не права ни одна модель, — дольше всего. Времена берутся из настоящих
ответов этого человека. Порядок показа — важность, умноженная на вероятность ошибки
и делённая на время.

**Что не меняется.** Приоритет «человек > голосовой профиль > распознавание > эвристики».
Порядок ничего не решает за человека и ничего не снимает: непоказанные места остаются
открытыми и помеченными в стенограмме, запрет цитат при открытых местах действует.

### Этап 5.1: решения владельца (22.11.2026)

Мера: разбор в пределах 20 минут на час записи. По числам этапа 5.0 прежнее наполнение уровня
«обязательно» (любой возможный пропуск речи и любое расхождение в корне слова) — около
227 мест на час записи, примерно 80 минут. Поэтому решено:

- **«Обязательно»** — технические сбои, паузы от 2 секунд и расхождение в корне у важного
  слова (число, имя, отрицание). Оценка — 33–71 место на час, 12–24 минуты; это границы
  расчёта по опубликованным итогам, не замер. Это заменяет прежнее наполнение уровня.
- **Доли времени** из 20 минут: около 13 — слова и паузы, 5 — кто говорит в содержательных
  репликах, 2 — случайная проверка остального; неиспользованное переходит дальше. Без долей
  вопросы «кто говорит» (больше половины мест) в разбор почти не попадают.
- **Паузы от 2 секунд** показываются все, даже сверх отведённых минут; программа пишет
  превышение.
- **Одновременная речь**: в 20 минут — только места с важным словом, остальные — отдельной
  очередью со счётчиком. Сколько таких мест, не считалось; считать при подготовке кода.
- Считать в минутах, а не в штуках: в 20 минут помещается от 40 до 100 мест в зависимости
  от того, сколько ответов человек пишет сам.

Не решено: нижняя граница минут для коротких записей; собирать ли новую порцию карточек
только после применения ответов прежней.

Очерёдность: код 5.1 — после правок этапа 6.1 о сохранении ответов и о паузах (те же файлы
и общая граница «слова паузы»). До этапа 7.2 каждое событие показа карточки делает свёртку
устаревшей, поэтому измерять разбор по событиям раньше 7.2 нельзя.

### Что показал этап 5.0

Числа, способ расчёта и ограничения —
[research/rar-5-0-review-effort-measure-2026-11.md](research/rar-5-0-review-effort-measure-2026-11.md).
Замер сделан по записям одной установки: 2204 места, решено 14 %. Что он меняет в плане:

- **Стартовые уровни для этапа 5.1.** «Обязательно»: возможный пропуск речи (правка в 52 %
  решённых) и места, где варианты моделей различаются корнем слова (текст изменён в 45 %).
  «Желательно»: места с близкими голосами и наложением речи (правка в 26–34 %), споры
  моделей. «По желанию»: места только с низкой уверенностью слова (правка в 6 %) и места
  без признаков важности, которых две трети.
- **Больше половины мест связано с голосом и наложением,** а не со словами. Перебор моделей
  распознавания (РАР-4) их число не уменьшит; для них важнее порядок по длине реплики
  и по тому, попадает ли она в свёртку.
- **Объединение точных повторов отложено:** схлопнулось бы 6 % мест, среди споров
  моделей — 1 %.
- **Полный разбор — около 3–4 часов на час записи** при 15–25 секундах на место. Поэтому
  в этап 5.1 входит отведённое время: человек задаёт минуты, программа показывает столько
  мест сверху, сколько в них помещается.
- **Замер смещён:** человек решал места не в случайном порядке, а «без правки» не отличает
  согласие от закрытия без прослушивания. Поэтому в этап 5.1 входят сохранение событий
  показа карточек и небольшая случайная доля мест из нижних уровней в каждом разборе:
  без неё уровни нечем проверить.

**Связь с другими направлениями.** РАР-4 меняет число спорных мест набором моделей, РАР-5 —
порядок их показа; мера у обоих одна — время человека. РАР-3 использует то же правило
«несколько самых сильных мест вместо порога».

**Дополнение 22.11.2026.** На прогоне через веб-формы измерено время между ответами
(75 ответов одного человека, одна запись): готовый вариант — 11–17 секунд; свой текст,
смена говорящего и вставка в пропуск — около 30 секунд. Это согласуется с оценкой
«15–25 секунд на место» и даёт исходные числа для исследования И7 (РАР-6). Примерно
четверть мест прогона была с одновременной речью.

**Расчёт по категориям владельца (исследование И4, 22.11.2026).** Числа, определения и
ограничения —
[research/rar-i4-review-categories-2026-11.md](research/rar-i4-review-categories-2026-11.md).
По 2345 местам той же установки: «очевидное» — 5 % (от 2 до 23 % в зависимости от строгости
правила), «неважное» — 17 %, «одновременная речь» — 26 %, остальное — 52 %. Что это меняет
в плане этапа 5.1:

- **Отбор по трём категориям сокращает основную очередь примерно вдвое, но не снимает
  вопрос времени:** остаётся около 1,7 часа разбора на час записи, ещё около часа — отдельная
  очередь одновременной речи. Порядок мест по пользе и отведённое время нужны по-прежнему.
- **«Неважное» нельзя скрывать одним уровнем.** Короткие «угу» и «ну» правятся редко, а паузы
  от 2 секунд человек чаще заполнял словами (11 из 18 решённых): длинная пауза чаще скрывает
  настоящую речь. Паузы от 2 секунд не скрывать.
- **Для «очевидного» данных нет:** решённых человеком мест этой категории в базе нет.
  Скрывать по умолчанию можно только по строгому правилу и со случайной долей на проверку.
- **Одновременная речь — отдельная очередь, скрывать её нельзя:** решённые человеком места
  изменены больше чем в половине случаев. Четверть очереди — реплики короче секунды.
- Категории удобнее хранить как независимые признаки места (слово, содержание, голос),
  а уровень показа выводить из них по настройке.
- У двух третей решённых мест нет следа человека: неизвестно, кто и как их закрыл. Это ещё
  один довод за ответы строками с автором (этап 6.2).

Вторая часть исследования — меняется ли конспект, если места не разбирать, — не сделана:
нужны два конспекта одной записи по полной и сокращённой очереди.

**Решения владельца:** сколько минут на час записи считать обычным временем разбора — от
этого зависит, сколько мест попадает в уровень «обязательно»; где делать показ соседних
вопросов вместе и подтверждение смены говорящего — в этапе 5.1 или в проекте схемы 6.2.

## РАР-6. Локальный интерфейс

**Зачем.** 21–22.11.2026 владелец прошёл весь путь записи через экран процесса и страницы
карточек без ИИ-агента. Итог: работать через нынешние страницы тяжело, а примерно половина
находок — ошибки логики применения ответов, которые экран только показал. Направление
отвечает на два вопроса: на чём строить интерфейс, который сам подстраивается под компьютер
и телефон, и что в программе надо изменить, чтобы им могли пользоваться несколько человек.

Основания, сравнение вариантов, источники и перечень непроверенного —
[research/local-interface-2026-11/README.md](research/local-interface-2026-11/README.md).

### Решения владельца (22.11.2026)

1. **Очерёдность:** сначала логика применения ответов, потом экраны.
2. **Устройства:** компьютер и телефон в домашней сети. Браузеры: на компьютере Firefox
   ESR, Chrome, Яндекс Браузер; на телефоне (у большинства Android) Firefox, Яндекс
   Браузер, Chrome.
3. **Что должно стать удобным:** разбор карточек, запуск и ход обработки, чтение и правка
   стенограммы, конспект со связкой «свёртка — стенограмма — аудиозапись». Пробным экраном
   может быть экран карточек, но продуманный заново.
4. **Клиент и сервер** — основа и для будущего сетевого сервиса; сетевой сервис для
   посторонних людей — примерно через год.
5. **Несколько пользователей:** структура таблиц закладывается сразу. На время обкатки все
   пользователи доверенные (владелец и ещё несколько разработчиков). Итоговое решение по
   спорной карточке может принять любой участник; записывается, кто и когда его принял.
6. **Шифрование** отложено на время обкатки логики обмена и форм.
7. **Голос:** быстрое распознавание на домашнем компьютере — да, оно сохраняет
   конфиденциальность. Рассмотреть функцию диктовки и простой расшифровки без разделения
   по голосам. Есть ли на телефоне пакет диктовки для работы без сети — дело пользователя.
8. **Сборка с Node.js** не решена: требует отдельных изысканий (исследование И1 ниже).

### Что выбрано

| Вопрос | Выбор | Почему |
|---|---|---|
| Форма | один веб-интерфейс в браузере для компьютера и телефона | нативные оболочки — переписывание; телефону отдельное приложение пока не нужно |
| Сервер | один сервер на Starlette и uvicorn вместо двух на `http.server` | пакеты уже стоят как зависимости `mcp`; запрос части звукового файла, поток событий о ходе обработки, одна точка проверки адреса запроса |
| Обмен | набор запросов, которым пользуется экран; тот же набор — для будущего приложения и сервиса | клиент и сервер разделены с первого шага |
| Клиент | пробный экран без сборки: готовые адаптивные компоненты локальной копией, тесты в настоящем браузере на Python | нет Node и чужих библиотек из общего хранилища у разработчика; установка из клона не меняется; переход к сборке — по итогам пробы |
| Ответ на карточку | всегда текст в поле; кнопка записи отправляет звук на компьютер и сразу возвращает текст в то же поле | исчезают отложенное распознавание и второй вид ответа; человек видит и правит результат |
| Телефон на время обкатки | по адресу домашней сети без шифрования: чтение, прослушивание, ответы касанием и текстом, диктовка клавиатуры; кнопка записи — только на компьютере | без шифрования браузеры не дают странице микрофон |
| Телефон после обкатки | шифрование со своим центром сертификации и мастером установки; сопряжение по QR-коду | единственный способ без интернета и внешних сервисов, при котором работает микрофон |
| Мобильное приложение | позже, как второй клиент или оболочка вокруг тех же экранов | цена распространения; проблему доверия сертификату не снимает |
| Модель распознавания на телефоне | не сейчас | готового решения для браузера нет; размер, скорость и лицензии сборок не проверены |

Что остаётся в силе при любом этапе: по умолчанию сервер слушает только `127.0.0.1`; доступ
из домашней сети выключен и включается человеком; устройство подключается сопряжением
с подтверждением на компьютере и может быть отозвано — это нужно и без шифрования, иначе
экран откроет любой, кто подключён к той же сети; облачные вызовы, скачивание моделей,
установка пакетов и перенос данных согласуются отдельно; распознавание речи средствами
браузера не используется.

### Требования владельца к экрану карточек

Опыт разбора на прогоне 21–22.11.2026 свёлся к трём категориям мест:

- **(А) Очевидное.** Часто просят подтвердить место, где слово произнесено неполно, без
  каких-то звуков, а говорящий очевиден.
- **(Б) Неважное.** Длинные паузы с посторонними звуками и неразборчивые короткие «угу»,
  «ммм», «вот», «ну».
- **(В) Одновременная речь** — самое тяжёлое: неудобно и трудно на слух, приходится
  переслушивать по нескольку раз. Второй человек коротко поддерживает основного: повторяет
  другими словами, показывает понимание, уточняет, подсказывает формулировку. Такие места
  важны только для точности дословной стенограммы; на выводы и конспект могут не влиять.

Что должно быть на экране:

1. автоматическое проигрывание фрагмента с указанием в стенограмме текущего момента;
2. сдвиг границ фрагмента: шире назад и шире вперёд;
3. соседние вопросы показываются и подсвечиваются вместе;
4. отдельное подтверждение смены говорящего: программа переставляет реплики между
   говорящими при одновременной речи и на фразах короче секунды;
5. вариант раскладки: вопрос и поле ответа вверху карточки, а не внизу;
6. вариант раскладки: два столбца, слева «как было», справа «как будет», с учётом уже
   записанных ответов;
7. согласие, отказ и выбор говорящего — кнопками; свободный текст в поле ответа означает
   только слово стенограммы (решение владельца 22.11.2026).

Почему пункт 7. Сейчас программа угадывает смысл свободного ответа по спискам фраз:
«верно», «всё правильно», «не совсем верно». Приёмка правок этапа 6.1 показала, что такие
списки нельзя закончить: каждая новая формулировка требует правки, а правка одного списка
ломает соседний. Кнопка не требует толкования. До пробного экрана (этап 6.4) действует
таблица коротких ответов, одна для текста и голоса; одиночное «нет» в поле ответа остаётся
словом стенограммы, а не отказом.

Что из этого следует для отбора мест (общая часть с РАР-5):

- при уровне тщательности «для конспекта» места категорий А и Б по умолчанию не
  показываются; при уровне «дословно» для них есть одно действие на всю группу;
- места категории В идут отдельной очередью для дословной стенограммы, с быстрыми
  действиями «перенести другому говорящему», «склеить с соседней репликой», «наложение,
  не важно»;
- автоматика помечает место только как «вероятно поддакивание» и ничего не решает за
  человека; непоказанные места остаются открытыми и помеченными, как в РАР-5.

Пункты 3 и 4 и отбор по категориям — не только экран: они меняют то, как места объединяются
в группы и как записывается перестановка реплик. Это часть этапов 6.1 и 5.1.

### Этап 6.1: состав и решения владельца (22.11.2026)

План этапа с воспроизведением причин на синтетических данных лежит в приватном служебном
репозитории. Каждая правка — отдельный PR; схема базы, аудио и голосовые профили этапом не
затрагиваются.

Состояние на 23.11.2026. Первая правка волны 1 — честные кнопки при конфликте документа — слита (PR №91); её остатки, которые владелец велел исправить до обновления установки, закрыты PR №102 с записанными ограничениями (они перечислены в документе экрана, раздел «Известные ограничения»), а резерв базы при повреждённой копии правки создаётся с предупреждением (PR №104). Правки об именах и метках (PR №89) и об отрицании (PR №90) слиты. Правку об ответах, которые не теряются, владелец решил делить на три части; первая утверждена 23.11.2026, две другие согласуются после неё. Правка об обязательном авторе правки отрезка идёт после всех трёх частей. Выводы для порядка работы: одна причина — один PR; во время работы запускаются тесты изменённых модулей, полный набор — один раз в проверке CI на Windows.

Известные ограничения ответов на карточку. Первые два владелец предварительно («скорее
всего», 22.11.2026) оставил до кнопок этапа 6.4:

- ответ из списка отказов PR №90 («неверно», «неправильно», «не согласен» и подобные) нельзя
  вписать как слово стенограммы: место остаётся открытым, хотя подсказка просит вписать слово;
- отказ вне списка («нет, это неверно») печатью записывается словами; «не, правильно»
  считается отказом; на карточке «Кто говорит» подсказка после отказа просит слово вместо имени;
- голосом «не Анна» при вариантах-именах выбирает Анну;
- после применённого варианта цепочка «отказ, затем верное слово» теряет слово, а согласие
  текстом или «наверно» голосом отменяет правку. Это предмет правки об ответах, которые
  не теряются.

| Волна | Что исправляется |
|---|---|
| 1 | Кнопка при конфликте документа не выдаёт замену файла за сохранение правки: «скачать мою правку» и «заменить файл версией программы» — два разных действия. Ответ на карточку не теряется и не превращается в подтверждение, которого человек не давал. У правки отрезка автор указывается при каждом вызове, умолчания нет. Имена и метки говорящих в тексте ответа понимаются правильно |
| 2 | Файлы проверяются до записи в базу. Пропущенная речь не захватывает соседнее слово. Свой ответ человека на карточке «модели расходятся» считается прослушиванием и закрывает место |
| 2б | Карточка противоречия. Поручение ИИ. Подтверждение действий человека окном программы |
| 3 | Конфликт документов виден сразу при открытии. Устаревшая проверка свёртки сообщает о себе. Ответ ложится на подсвеченное слово. Изменённый ответ применяется целиком или никак |

Решения владельца, по которым построена волна 2б:

- **Ручная правка отрезка слабее ответа на карточке.** Если они противоречат друг другу,
  программа заново собирает одну карточку именно об этом противоречии: варианты, свой
  текст и отдельное примечание человека.
- **Поручение ИИ.** Человек сам решает, работает ли ИИ за него и в какой части: на всю
  программу, на группу, на запись или на отдельное место. Цель — экономия сил человека,
  а не точность. Пока человек не выбрал, ИИ только предлагает. По поручению ИИ может
  закрыть место «модели расходятся» с отметкой «не прослушано»; такое место не может
  держать цитату. Выбор говорящего можно поручить только явным выбором человека; в
  умолчание он не входит и в голосовые профили не идёт. Пока соответствующая правка
  `AGENTS.md` не согласована, действует прежнее правило: агент не выбирает автора спорной
  реплики.
- **Одно окно подтверждения** программы — на применение ответов, проверку, замену файла,
  возврат версии и на расширение поручения ИИ.
- **Приёмку** разрешено вести на копии материалов прогона в песочнице; живая запись не
  трогается.

Что этап меняет для пользователя: программа чаще будет отказывать вместо молчаливой записи;
прежние вызовы правки отрезка без автора перестанут работать; то, что агент раньше делал
молча, станет предложениями, пока человек не дал поручение.

**Связь с другими направлениями.** РАР-5 определяет порядок и уровни показа мест; РАР-6 —
где и как человек на них отвечает. Сохранение событий показа карточек (этап 5.1) и ответы
строками с автором (этап 6.2) — одна и та же запись, её надо проектировать один раз.

**Как ведётся этап 6.1 (решение владельца 22.11.2026).** Вместо слова на каждую правку —
поручение на волну: владелец один раз утверждает список правок, разрешённые файлы и границы;
внутри него координатор ведёт разработчика и приёмщика на разных моделях. Правки, меняющие
запись ответов, файлы рядом с аудио, подтверждения или договор с агентами, сливаются по
слову владельца один раз на волну; правку, которая этого не меняет, агент сливает сам при
зелёных проверках на Windows и приёмке без расхождений; обновление установки, данные, облако,
модели и пакеты — всегда отдельным решением владельца. Поручение на волну 1 утверждено
22.11.2026. Папки записей у владельца — на обычном локальном диске, без облачной
синхронизации; файл стенограммы открывается в простом редакторе, который его не блокирует.

**Решения владельца, которые ещё нужны:** согласование каждого этапа; для этапа 6.1 — слово
на слияние каждой волны и ответы на вопросы плана (чем закрывать паузу без слов; что значит «да» в поле ответа; служебная
строка в файле свёртки; чинить ли файловый режим хранения; что делать с уже записанными
неверными отметками); текст правки `AGENTS.md` о поручении выбора говорящего; сборка
с Node.js — по итогам И1; способ шифрования — по итогам И5, вместе с уточнением, отложено
оно или не нужно; какие поля спрашивать у человека при подключении устройства (имя
участника, имя устройства).

## РАР-7. Путь свёртки

Индекс введён владельцем 22.11.2026. Запись в план не разрешает менять код: каждый этап
начинается с плана и слова владельца.

**Цель и мера.** Свёртка должна быть годной, когда человек разобрал карточки сомнительных
мест в пределах 20 минут на час записи. Сравнивать — с конспектами, которые делал ИИ-агент.

### Что установлено проверкой (22.11.2026)

Проверено запуском на синтетических записях в песочнице, без облака и без настоящих записей.

- После 20 минут разбора открытыми остаются около 590 мест из 650 на час. Одно открытое
  место запрещает цитаты на всю запись.
- Если у открытого места нет ссылок на слова (так у всех свежих мест и у пауз), задание
  помечает сомнительными все слова записи: разбор не меняет того, что видит модель, пока
  не закрыто последнее место.
- Событие показа карточки, сборка пакета карточек или сохранённый ответ создают новую
  ревизию разбора. Если это случилось, пока облачная модель отвечает, шаг падает после
  оплаченного вызова, и продолжить его нельзя. Готовая свёртка после одного показа карточки
  считается отсутствующей, проверка человеком снимается. Сам пакет карточек не устаревает.
- Запись длиннее 10 000 слов (около 80 минут) получает отказ, из которого у запроса нет
  выхода.
- Если блоки сохранены, а итог не записался, повтор отвечает «готово» без свёртки.
- Принимаются цитата с чужим автором и выдуманная цитата короче четырёх знаков; название
  в кавычках и подпись перед цитатой отклоняют весь ответ.
- Блоки по 500 слов — следствие договора: ответ обязан перечислить номера всех слов, и
  в предел размера ответа помещается около 800 слов.

Не проверено: настоящее облако (размер запроса, время ответа, соблюдение договора моделью,
качество) и настоящие записи.

### Решения владельца (22.11.2026)

- **Договор с моделью:** модель видит всю запись, а в ответе указывает границы раздела —
  «от реплики такой-то до такой-то» — вместо перечня всех слов. Полное покрытие проверяется
  по границам, связка «раздел — стенограмма — звук» сохраняется. На прототипе запрос меньше
  примерно в 12,8 раза, схема базы не меняется.
- **Цитаты:** запрет по каждой цитате, а не на всю запись. Чистая цитата — в кавычках.
  Задевшая неразобранное место печатается без кавычек с пометкой «по распознаванию,
  не проверено» и временем; после разбора места кавычки возвращаются при пересборке, без
  облака. Одна негодная цитата не отменяет свёртку.
- **Порядок:** черновик свёртки сразу после расшифровки; после разбора — кнопка «Обновить
  свёртку». Сама программа текст повторно в облако не отправляет. Прежний файл остаётся,
  пока не принят новый.
- **Длинная запись:** частями до предела, разрез по длинной паузе; с каждой следующей
  частью уходит изложение предыдущих. До этого — понятный отказ вместо тупика.
- **Облачная проба:** сначала синтетический текст, затем одна настоящая запись, которую
  назовёт владелец. Каждый запуск — по отдельному слову.

## Предложения, не принятые как направления

- **Голосовые профили по записям из SQLite.** Действующее ограничение
  ([development-boundaries.md](development-boundaries.md)), введено осознанно: открытый
  файл стенограммы из SQLite не содержит всего нужного для безопасного отбора, и простое
  снятие проверки привело бы к обучению по неполным данным. При хранении в SQLite профили
  читаются, но не пополняются: ручной пересчёт отвечает отказом, автопополнение пропускает
  такие записи без сообщения человеку. Предлагаемый путь: сначала сообщать причину
  пропуска, затем вернуть ручной пересчёт по снимку из базы с подтверждением человека;
  автопополнение — отдельным решением. Нужны решения владельца: что считать подтверждением
  человека в базе, что делать со старыми файлами рядом с аудио, нужен ли отзыв вклада при
  откате ревизии.
- **Связь между блоками свёртки и записи длиннее 10 000 слов.** Меняет состав и объём
  передаваемого облачной модели; проверяется только облачным прогоном.
- **Короткие номера слов в модельном задании** вместо длинных идентификаторов. То же
  условие проверки.
